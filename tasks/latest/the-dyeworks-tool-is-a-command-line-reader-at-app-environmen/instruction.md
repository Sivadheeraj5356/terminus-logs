The dyeworks tool is a command-line reader at /app/environment/dyeworks that parses a compiled dyeworks-tree container and prints a one-line JSON summary for a file that conforms to the format. The summary is one line carrying exactly these keys in this order and nothing else: `version`, `dyeworksdefs_defined`, `nodes_parsed`, `lots_resolved`, `indirects_resolved`, and `root_type`, where `version` is the unit format version, `dyeworksdefs_defined` is the count of type declarations, `nodes_parsed` is the number of non-null nodes, `lots_resolved` and `indirects_resolved` are the counts of resolved lot references and indirect forms, and `root_type` is the type name of the root node. The byte layout is documented in /app/environment/docs/dyeworks-format.md. Every file under /app/environment/testdata/valid conforms to the format, and each must keep parsing and printing the same summary, with the same keys, order, and values. Your changes go in the C sources under /app/environment/src and the headers under /app/environment/include, and dyeworks stays the same compiled C reader; there is no network access, so do not install anything.

The reader must accept exactly the files that conform to this format and turn away the rest. Every offset, size, count, and index a file carries is drawn from the file, so before the reader uses one it must confirm it against the file's real extent and against the structure the format says it names. A section conforms only when it lies wholly after the header and the section table and its length reaches no further than the bytes that follow its offset, so a section that points back into the header or table, or whose length reaches past the end of the file, does not conform. The container version must be 1. Each declaration names one of the format's types and each field one of the defined forms, so a declaration whose type or whose field form is not one the format defines is turned away when the declaration is read, even if no node goes on to use it. A unit's dyeworksdef offset must fall strictly inside the dyeworksdef section, so an offset equal to or past the section size names no declaration and is turned away. Every count, code, and `uleb` or `sleb` value is a LEB128 varint that conforms only when it fits its width (an unsigned 64-bit value for `uleb`, a signed 64-bit value for `sleb`) and spends no more groups than that width needs, so a varint that runs past its section, that is padded into an over-long encoding of more than ten groups, or that carries a value outside its 64-bit range does not conform and is turned away rather than decoded with bits lost. The format bounds a container's node nesting at 256 levels and a whole container at 64 MiB: a conforming file never nests deeper than 256 levels and is never larger than 64 MiB, and a file that nests deeper or is larger is turned away rather than followed without end. A container node's child chain is always closed by an explicit null node, so a child chain that reaches the unit end without its null terminator is turned away. An indirect form names a concrete form directly, and its value follows encoded in that named form, so an indirect form that names another indirect form does not conform and is turned away, and a finite indirect value resolves in one step. A file whose fields all stay within the structures they name is accepted and prints its summary unchanged; a file that departs from the format in any of these ways is turned away. Acceptance must not depend on a limit the format does not impose, or on particular file names or byte sequences.

A turned-away file is reported on stderr with a short message naming the part of the format that failed, reusing the names the reader already uses: header, sectab, uleb, dyeworksdef, node, form, lot, str, format. The reader then exits with a nonzero status. A conforming file is always accepted, and a nonconforming file is always turned away by an explicit, named error, with the valid corpus continuing to parse.
