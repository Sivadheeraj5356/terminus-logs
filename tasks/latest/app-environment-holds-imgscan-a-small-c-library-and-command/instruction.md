/app/environment holds imgscan, a small C library and command-line tool that a forensic examiner uses to inspect a compiled disk image (a `.dfi` file) before a filesystem would be mounted from it: an eight-byte superblock, a region table, and the names, volumes, inodes, links, and xattrs sections it points to. The reader walks the volume table, where each volume descriptor carries a label offset into the names pool, a signed base logical block address, and a feature-flags word; it walks the inode table, where each inode carries a fixed-width owner id, a signed modification-time delta, and then either a run of resident data bytes (a file inode) or a list of the inode indices of its children (a directory inode); it walks the hardlink table, whose edges index two inodes each, and the xattr table, whose attributes carry an inline length-counted value. To report the total resident footprint it resolves the root inode 0 through its directory tree, summing the resident data bytes the file inodes it reaches contribute. For a well-formed file it prints a one-line JSON summary whose keys are format_version, volumes_defined, inodes_defined, file_inodes, dir_inodes, hardlinks_parsed, xattrs_parsed, and data_bytes, the total resident byte count reachable from inode 0 with a directory resolved as the sum over the inodes it lists. The same inode may be listed more than once, and by more than one directory, and each listing adds that inode's footprint again, so data_bytes is counted with multiplicity. Each key is defined in the format reference. The format is documented in /app/environment/docs/disk-forensic-image-format.md. The build produces the native executable /app/environment/imgscan, linked against the Electric Fence guard-page allocator; keep it a native, Electric-Fence-linked binary. There is no network access.

The catch is that this reader loads images an attacker can craft byte by byte, and it currently trusts every offset, size, count, and index it reads from them, so a malicious image can read out of bounds, overflow an allocation, or drive the directory resolver into unbounded recursion. Harden the sources under /app/environment/src so no crafted file can corrupt memory or crash the reader, while every legitimate image still parses to exactly the same summary. When it turns a hostile file away it must do so cleanly: exit nonzero and print a short stderr message naming the subsystem that caught it, one of super, regtab, uleb, vol, inode, name, data, child, link, xattr, and never segfault or corrupt the heap. The images under /app/environment/testdata/valid are all legitimate, including deliberately extreme but well-formed ones, and must keep parsing unchanged; don't special-case particular files or byte sequences to force them through.

Two nuances for the directory resolver. A chain of directories nested far deeper than any real image is still legitimate as long as it is acyclic, so resolving it or turning it away are both fine, it just must not crash; a directory that refers back to itself is malformed and must be rejected. Separately, because the same inode can be listed many times over, an image whose directories share subtrees widely can have a resident footprint that runs high into the 64-bit range while the image itself stays small, and such an image is still well-formed: its footprint must be reported exactly and in bounded time.
