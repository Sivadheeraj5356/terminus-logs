Journal rows are applied in ascending `seq` order. Rows sharing a `seq` are identical only when their parsed `op`, `scenario_tag`, `cycle_epoch`, `ram_block_id`, and `event_id` fields match; identical repeats apply once, while a mismatch is a durable-sequence conflict that must exit non-zero before any requested final log or report is changed or created. For a non-empty `event_id`, only the first row in durable order applies. Normal seat runs append to an existing seat log without changing its prior bytes and assign new emitted `seq` values from one greater than the greatest existing value, or from 1 when no prior value exists. Recovery preserves every row that existed before the invocation byte-for-byte, inspects all valid pre-existing log rows, and begins newly emitted recovery rows at one greater than the highest existing integer `seq` (or 1 when no prior row exists), never from row count or the last physical line. Failed normal runs leave existing publications unchanged and do not create absent final paths. A retained `cycle_arm` row sets the ledger active `cycle_epoch` to the row's `cycle_epoch` value exactly without assuming contiguous epochs.

For `ram_seat`, publishing the same `ram_id` with the same CMPR block checksum at a strictly newer effective `cycle_epoch` must refresh that ram's stored cycle ownership in the live ledger without emitting another `ram_seated` log row and without increasing seated count; journal revision still advances so dependent views observe the change. Publishing the same checksum at the same or older effective epoch is a no-op. A different checksum is a revision that updates tonnage and emits one new `ram_seated` row. The effective epoch is the event's explicit nonzero `cycle_epoch` when present; otherwise it is the active cycle epoch at apply time.
