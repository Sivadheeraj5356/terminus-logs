Fleet hosts in US/Eastern run a nightly consolidation cron that keeps durable totals under /var/lib/acct and rebuilds an offline daylight-saving schedule history into /app/output/schedule_ledger.json. Disk, load, and cron.service probes stay green, but after local clock transitions the recorded schedule no longer matches what operators expect. Window indexes live under /app/data/windows/{backward,forward,resume}/window.conf (passed to step_tool as --env), fragment snapshots live under /app/data/traces, and the host-side rebuild helpers and policy sources live under /app/environment (including shared cadence settings in m5s/cadence_policy.conf).

Around the autumn fall-back weekend, one calendar day sometimes shows two completed runs with the same YYYYMMDD day stamp but different wall-time offsets inside the repeated local hour, and stored totals run high. Around the spring forward weekend, the civil hour that never exists on the local clock (ten-digit YYYYMMDDHH) is missing from the packed history: there is no service error line, only a hole in that day's schedule. After an ordinary host reboot, catch-up sometimes re-runs intervals that were skipped on purpose during the transition and inflates totals again, while genuine post-boot gaps can stay empty on later resumes. A rebuild that looks clean on the first pass can still be wrong on a later resume once the boot-era marker already exists, and civil keys for the same calendar day must stay consistent with the finest hour-level key already recorded while earlier windows were stepped.

Restore correct host schedule regeneration so stepping the three daylight-saving windows yields a consistent /app/output/schedule_ledger.json. Repair sources under /app/environment, rebuild with `make -C /app/environment`, refresh /app/tools/step_tool and /app/tools/pack_tool from the build products, then follow the operator sequence in /app/environment/docs/step_tool.md. A rebuild steps the windows in order, leaves shared state under /app/output/step (including /app/output/step/commit_log.tab and /app/output/step/boot_era.rec), and packs both the rows array and the ledger_digest field. Fall-back must collapse the repeated wall hour to one run per calendar day; spring-forward must still record the absent civil hour once; resume must record its post-boot gap on the initial first pass while keeping later catch-up recovery from replaying intervals that were skipped on purpose during the transition.

On a warm resume re-step—after boot_era.rec already exists—the first pass must defer boot-gap fragments because the era marker is present, and emit only the timezone-skip row (for example civil_key 20240311). The commit log does not gate that first-pass deferral; it only decides whether the later recovery pass may emit an uncommitted boot-gap interval. Without era-based deferral the pane looks fine on a cold rebuild and fails only when resume is stepped again with a warm era. That is different from packing the same stepped tree twice, which must keep ledger_digest stable, and from a cold full rebuild, which still carries both first-pass resume rows.

The graded checker follows the documented command sequence under /app/environment/docs and rejects hand-written ledger files or intermediate pane artifacts that were not produced by that pipeline. It also compares stepping the windows one at a time against stepping them together, detects stale hand edits to intermediate rows.tab files, and checks the warm-era resume re-step behaviour above. For the digest algorithm, per-window schedule rules, commit-log semantics, boot-era timing, and the exact rebuild commands (including each pane's window.conf path), read /app/environment/docs/ledger_format.md and /app/environment/docs/step_tool.md. Static or manual output writes are insufficient; wrapper-only or fixture-only edits are insufficient.
