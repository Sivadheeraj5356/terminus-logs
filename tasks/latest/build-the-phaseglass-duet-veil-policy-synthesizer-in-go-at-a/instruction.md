Build the Phaseglass Duet veil-policy synthesizer in Go at "/app/cmd/phaseglass-duet". It must build with the provided Go toolchain and run as "go run /app/cmd/phaseglass-duet --board /app/boards/public.json --output /app/out/phaseglass_policy.json". A board contains several possible hidden world states, and the program never learns the hidden state directly. At each nonterminal policy node it chooses one simultaneous Amber/Cobalt action pair, observes movement results and beacon signals, and then the environment may adversarially choose any successor allowed by the joint tone. The observation is produced before that hidden transition, so one observation can lead to an expanded belief containing several successors. The chosen action pair must be legal and must avoid collisions, direct swaps, and tether violations for every hidden state in the current belief. A policy succeeds only when every possible run reaches both goal rooms in accepting hidden states within "max_turns"; reaching the rooms while any possible hidden state is non-accepting is not terminal.

Find the exact best strong policy, comparing candidates by lower worst terminal turn, lower worst boost count, lower worst energy, lower sum of each initial world's worst terminal turn across all allowed drift choices, and finally the lexicographically smaller complete recursive policy using the action and observation orders in the rules file. Output a canonical breadth-first policy DAG: assign IDs "N0", "N1", and so on by visiting branches in bytewise observation order, and reuse one node whenever tick, positions, charges, boosts, energy, and sorted belief are identical. The root JSON members, in order, are "schema_version", "board_id", "status", "worst_turns", "worst_boosts", "worst_energy", "total_turns", "policy_nodes", "root", and "nodes"; "schema_version" is exactly "phaseglass.policy.v3". Every node contains, in order, "id", "tick", "amber", "cobalt", "charges_left", "boosts_used", "energy", "belief", "terminal", "action", and "branches". Nonterminal actions contain "amber" then "cobalt" and use "wait", "listen:<beacon_id>", "move:<edge_id>", or "boost:<edge_id>". Branches contain "observation" then "next" and are bytewise sorted. Terminal nodes use action null and branches []. A successful strong policy must use status exactly "solved"; when no strong policy exists, status is exactly "unsolved" with zero metrics, root "", and nodes []. Empty arrays are always [], never null.

The built Go command must be self-contained at runtime and must not depend on shell commands or other external executables.
