# PFSEAL2 cryptographic incident ledger contract

`/app/sql` records the production incident-ledger definitions. The verifier may assume those tables and columns exist, but not that records arrive in insertion order. All SQL must work in DuckDB and use the security evidence database selected by `--db`; creating a second database or sidecar state is not supported.

`prefect_secret_jobs` is the incident intake ledger. Eligible records are `pending` records and `processing` records whose `lease_until` is at or before the verifier's effective `--at` time. Select the smallest eligible `job_id`. Before issuing any claim `UPDATE`, committing a claim, incrementing `attempt_count`, or changing lease fields, validate the selected record's `job_id` and `metadata_revision` as non-negative JavaScript-safe integers. Either unsafe value is a fatal database error: roll back the read/claim transaction, leave the record completely unchanged, print the fatal verifier error, and exit 70. Only after both checks pass may a claim change the state to `processing`, increment `attempt_count`, and write the owner and a lease exactly 60 seconds after the effective time. Completed and failed records are terminal and are never reclaimed.

Each job joins one row in `prefect_images`; `image_annotations_json` must parse as a JSON object and contain exactly one valid direct or chunked transport from `/app/docs/pfseal2-wire.md`. A missing image, invalid annotations JSON, absent transport, simultaneous transports, or malformed transport is an envelope-format failure. Deployment policy comes from `prefect_deployments`: the job revision must be within `valid_from_revision` and `valid_through_revision` (inclusive), and `minimum_readable_key_version` must not exceed `active_key_version`.

A successful security decision finalizes in one transaction: recheck and upsert `prefect_secret_state` with the payload counter, plaintext SHA-256, and effective verifier time; append the deployment audit chain and the global snapshot plus append-only event-MMR transparency checkpoint; conditionally insert a containment rotation row using the envelope version, active version, secret name, and effective time; then mark the incident `succeeded`. Both terminal outcomes set `completed_at` to the effective time and clear the lease owner and deadline. Success clears `failure_code`; a rejected incident stores its public code and creates no audit, state, head, checkpoint, or rotation mutation. The verifier does not put plaintext in DuckDB. If a database write fails, roll back that finalization transaction, leave the incident in its leased `processing` state, stop with exit 70, and print only the fatal error line required by the interface contract.

`pfseal_audit_heads` chains successful records independently per deployment. With no head, the next sequence is 1 and the previous hash is 64 zeroes; otherwise the next sequence is `last_sequence + 1` and the previous hash is `last_audit_hash`. Existing head hashes must be lowercase 64-character hex and sequences must be JavaScript-safe unsigned integers, or finalization is fatal. The new `audit_hash` is lowercase SHA-256 hex of UTF-8 `PFSEAL-AUDIT-V1\n` followed by canonical JSON containing exactly these sorted fields: `activeKeyVersion`, `auditSequence`, `deploymentId`, `envelopeKeyVersion`, `headerSha256`, `imageDigest`, `jobId`, `keyAttestationSha256`, `metadataRevision`, `plaintextSha256`, `previousAuditHash`, `processedAt`, `rotationCounter`, `rotationDecision`, `secretName`, and `workerId`. The audit row and head store that same sequence and hash.

Rerunning the verifier is idempotent because terminal incidents are not eligible and evidence tables use stable primary keys. Database values for ids, revisions, counters, and audit sequences are unsigned 64-bit values; JSON and hash inputs may use numbers only when they are within JavaScript's safe integer range. Values outside that range cause a fatal database error rather than lossy output.
