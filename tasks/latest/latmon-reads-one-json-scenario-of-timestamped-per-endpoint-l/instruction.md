`latmon` reads one JSON scenario of timestamped per-endpoint latency samples on standard input and writes one canonical JSON alarm ledger on standard output. Build it with `go build -o latmon ./cmd/latmon` and run it as `./latmon < scenario.json > ledger.json`. Your job is to implement the missing computation that turns a validated scenario into its ledger. `latmon` already reads standard input, validates it, and writes standard output; leave that wiring and the command-line interface as they are.

Every quantity is an integer: timestamps, latency values in ms, and the `limit`, `arm`, `reset`, and `budget` parameters measured in seconds (except `limit`).

The input is a JSON object with an `endpoints` array, a `samples` array, and an optional integer `until`. Each endpoint has a unique non-empty `name`, an integer `limit` (the over-limit threshold in ms), and three non-negative integers `arm`, `reset`, and `budget`. The `samples` array is a shared stream; each entry names a configured `endpoint` and an integer time `t >= 0`. An entry's `type` is `"sample"` (the default when absent), `"service"`, or `"endservice"`. A `sample` entry additionally carries an integer `latency`; a `service`/`endservice` entry carries no `latency` and opens/closes a service window for its endpoint (see below). `until` is optional. Each endpoint's own timeline is the subsequence of entries naming it, processed in non-decreasing `t`; entries sharing a `t` are processed in array order.

A `sample` sets the endpoint's latency to its `latency` value from its own `t` until the next `sample`'s `t`; the last `sample` holds its latency until the horizon `H` (`until` when present, otherwise the largest `t` among all entries in the scenario). Before an endpoint's first `sample` it has no latency and cannot be over the limit. Service entries do not change the latency. A endpoint is over at any instant where its latency is strictly greater than `limit`, and under otherwise. Open alarms are truncated at `H`.

An alarm is a maximal stretch over the limit for one endpoint governed by two dwell timers, `arm` and `reset`, each counting elapsed continuous seconds and paused by service windows. When a endpoint becomes over at time `s`, it begins arming. The alarm is confirmed once the endpoint has stayed over continuously for `arm` seconds; that confirmation is a computed instant. If the endpoint returns under the limit before the arm dwell completes, the over-stretch was a transient and produces no alarm. A confirmed alarm's interval starts at `s` (the instant the endpoint first went over), not at the confirmation instant. Once confirmed, the endpoint is in the alarm while over. When it returns under the limit at time `r`, `r` is the alarm's tentative end. The alarm resets only after the endpoint stays under continuously for `reset` seconds; the computed reset instant becomes the alarm's end. If the endpoint re-breaches the limit during the reset dwell, the reset is abandoned, the in-progress alarm continues uninterrupted, and the next reset attempt starts from the next return-under instant. A computed boundary (confirm or reset) that coincides with a sample or service entry resolves before that entry.

A `service` entry opens a window at `t`; the matching `endservice` closes it at its `t`. During a service window the arm dwell, reset dwell, and alarm-second budget clock are all paused; time spent inside a service window does not advance any of them. A service window does not on its own begin arming, confirm or reset an alarm, return the endpoint under the limit, or re-breach it. Any phase change the samples imply is evaluated only when the window closes, against the latency in force at `endservice`, and takes effect at that `endservice` instant (so an over-to-under return inside a window has return time = the `endservice` instant, and a stretch that first goes over inside a window begins arming at the `endservice` instant). A `service` while a window is already open, an `endservice` with no open window, and a window still open at the end of an endpoint's timeline are all malformed input.

`budget` bounds the cumulative confirmed alarm-time an endpoint may accrue before it locks out. Alarm-seconds are counted only while a confirmed alarm is over, and only from the confirmation instant onward; arming seconds, under-limit seconds of a merged dip, and any seconds inside a service window are not counted. The running total accrues in real time as the endpoint stays over. The endpoint locks out at the exact instant cumulative confirmed alarm-seconds reaches `budget`, even when that instant is strictly between two samples. Lockout is a one-way latch: at the lockout instant the endpoint's currently open alarm (if any) is truncated to end there, no later alarms are reported for that endpoint, and `alarm_seconds` is reported as `budget`. `locked_at` is that instant, or `null` if the endpoint never locks out. With `budget` equal to `0` a endpoint locks out at its first confirmation instant.

The output is a JSON object with an `endpoints` array ordered by `name` ascending (byte order), containing every configured endpoint, including those with no samples or no alarms. Each entry has: `name`, `alarms` (confirmed alarms in time order, each a half-open interval `[start, end)` with `start < end`; transients and zero-length intervals omitted), `alarm_seconds` (cumulative confirmed alarm-time, capped at `budget` once locked out), `locked_at` (the lockout instant or `null`), and `final` reporting the state at horizon `H`. `final.state` is `"locked"` if the endpoint locked out, `"active"` if a confirmed alarm is in progress and over at `H`, otherwise `"ok"`. `final.since` is the instant the endpoint entered that state: the lockout instant when locked; the in-progress alarm's start when active; otherwise the instant the endpoint last became ok (the end of the last confirmed alarm, the tentative return time if a reset dwell is still pending at `H`, or `0` if the endpoint never had a confirmed alarm).

If the input is not a JSON object, is missing `endpoints` or `samples`, names a duplicate endpoint, omits an endpoint or sample field, carries a negative `arm`, `reset`, `budget`, or sample `t`, gives two samples the same `t` for one endpoint, references an unknown endpoint, carries an unknown entry `type`, attaches a `latency` to a service entry, opens a service window while one is already open for that endpoint, closes one that is not open, leaves a service window open at the end of an endpoint's timeline, or sets `until` before the last sample: write a diagnostic to standard error and exit nonzero without printing a ledger.
