# GammaSpec Methods Bundle, Orion bench revision 9.5

This bundle is the lab-maintained source document for the GammaSpec fitting API used on the Orion detector bench. It is not a tutorial and it is not intended to be padded reading material: every normative section below is tied to a service requirement, a route contract, or an operational audit finding that the TypeScript service in `/app` must satisfy. The companion `/app/docs/00_gammaspec_contract.md` front-loads the same endpoint shapes for quick implementation review, while this document remains the citation target for compliance matrix `source` fields: `/app/docs/gammaspec_methods.md#<requirementId>`.

The Orion bench emits short spectra from a fixed detector and a fixed calibration file. The API still has to behave like production analysis code: it must preserve detector identity, use calibrated energy rather than channel numbers for model construction, reject physically impossible timing, carry background subtraction through uncertainty calculations, avoid nondeterministic bootstrap intervals, keep batch runs isolated, and leave file descriptors stable under repeated requests. The requirement IDs below are the authoritative change-control keys used by the lab review board.

## GammaSpec service wire contract

All spectrum-like requests use `channels: number[]`, `counts: number[]`, `isotope: string`, `liveTimeSec: number`, and `realTimeSec: number`. Unknown isotopes, malformed numeric arrays, `liveTimeSec <= 0`, `realTimeSec < liveTimeSec`, invalid bootstrap iteration counts, and non-integer bootstrap seeds return HTTP 400 JSON. Optional `background` is a nested object with exactly `counts: number[]`, `liveTimeSec: number`, and optional `label: string`; the background count length must match the spectrum length and its live time must be positive. The detector id is always `GS-ORION-17`.

Every response object that contains `normalization` uses exactly these five fields: `liveTimeSec`, `realTimeSec`, `deadTimeCorrection`, `backgroundSubtracted`, and `backgroundScale`. `backgroundSubtracted` is a boolean; the other four fields are numbers. The normalization object does not contain raw counts, corrected-rate arrays, variance arrays, source labels, nested background objects, or request copies. Canonical quality flag strings are exactly `tail-model-applied`, `background-subtracted`, `dead-time-corrected`, and `high-reduced-chi-square`, emitted in that order when their condition applies. The tail flag is emitted for the four-term fit, the background flag only when a background object is accepted, the dead-time flag when `deadTimeCorrection > 1.0005`, and the high chi-square flag when `reducedChiSquare > 3.0`. Diagnostics may append `residual-review` after those four.

`POST /fit` returns `detectorId: "GS-ORION-17"`, `method: "poisson-readout-tail-wls-r4"`, `weighting: "poisson_readout_live_rate_inverse_variance"`, `calibrationApplied: true`, `modelTerms: ["gaussian", "lowEnergyTail", "constant", "linear"]`, `roi`, `coefficients`, a 4 by 4 `covariance`, `degreesOfFreedom`, `reducedChiSquare`, `normalization`, `qualityFlags`, `fittedRates`, and `residuals`. The `roi` object contains `count`, `energyMinKeV`, `energyMaxKeV`, `channelMin`, and `channelMax`; `coefficients` contains `amplitude`, `tailAmplitude`, `background`, and `linearSlope`.

`POST /bootstrap` returns `seed`, `iterations`, `statistic: "amplitude"`, `pointEstimate`, and `confidence` containing numeric two-element `ci68` and `ci95` arrays. The bootstrap is deterministic for identical payloads and seed values. Bootstrap iteration counts must be integers greater than or equal to 2; missing, non-integer, or smaller iteration counts return HTTP 400 JSON.

`POST /batch-fit` returns top-level `detectorId: "GS-ORION-17"`, `runCount`, `sortedBy: "runId"`, and `results` sorted by `runId`. When `includeResiduals` is absent or false, each result row contains exactly six keys: `runId`, `roi`, `coefficients`, `normalization`, `reducedChiSquare`, and `qualityFlags`. Compact rows must not include per-row `detectorId`, `isotope`, `method`, `weighting`, `calibrationApplied`, `modelTerms`, `covariance`, `degreesOfFreedom`, `residuals`, `fittedRates`, or nested `fit`. When `includeResiduals` is true, each result row contains exactly the same six keys plus `residuals` and `fittedRates`; it still omits nested `fit` and per-row identity/method metadata.

`POST /diagnostics` returns top-level `detectorId: "GS-ORION-17"`, request `isotope`, request `runId` when supplied, `method: "roi-hat-residual-diagnostics-r2"`, top-level `roi`, `normalizationRevision`, compact `fit`, `integrals`, `residualDiagnostics`, `decision`, and `qualityFlags`. The compact `fit` contains `coefficients`, `degreesOfFreedom`, `reducedChiSquare`, and `qualityFlags`. The `integrals` object contains exactly numeric `observedRateSum`, `fittedRateSum`, and `absoluteResidualRateSum`; `absoluteResidualRateSum` is the sum of `abs(observedRate_i - fittedRate_i)` over ROI points in corrected count-rate units, not a signed residual sum. The `residualDiagnostics` object contains exactly numeric `weightedMeanRate`, `weightedRmsRate`, `maxAbsInternallyStudentized`, `maxLeverage`, and `reviewThreshold`; the first two are weighted residual mean/RMS metrics, not unweighted summaries of observed rates.

`POST /isotope-screen` returns `detectorId: "GS-ORION-17"`, `method: "candidate-isotope-wls-aicc-screen-r1"`, `sortedBy: "aicc"`, `candidateCount`, and `candidates` sorted by increasing AICc. Candidate rows contain `rank`, `isotope`, `aicc`, `deltaAicc`, `amplitude`, `reducedChiSquare`, `qualityFlags`, and `roi`. AICc is computed from weighted SSE exactly as defined in the numerical block.

## Normative numerical algorithm block

This block resolves implementation ambiguity in the surrounding lab prose. Implementations may organize code differently, but observable JSON values must be produced from these definitions without rounding or truncating intermediate values.

1. Load `/app/data/calibration.gamma.json` once into process memory. For channel `c`, calibrated energy is `offset + slope*c + quadratic*c*c`. The ROI is every input index whose calibrated energy satisfies `abs(E - peak.energyKeV) <= peak.roiHalfWidthKeV`, preserving the request order. Unknown isotope names are request errors.
2. `deadTimeCorrection = realTimeSec/liveTimeSec`. With background, `backgroundScale = liveTimeSec/background.liveTimeSec`; without background, `backgroundScale = 0`. The corrected observed ROI rate is `y_i = (counts_i - backgroundScale*background_i) * deadTimeCorrection / liveTimeSec`.
3. The weighted fit is in calibrated energy space with columns `gaussian`, `lowEnergyTail`, `constant`, and `linear`. For energy `E_i`, `gaussian = exp(-0.5*((E_i-center)/sigma)^2)`, `lowEnergyTail = exp((E_i-center)/tailDecayKeV)` for `E_i <= center` and `0` otherwise, `constant = 1`, and `linear = E_i-center`. The `lowEnergyTail` column is a standalone one-sided exponential basis, not a Gaussian multiplied by an exponential.
4. Variance for inverse-variance weighting is `(max(counts_i, 1) + backgroundScale^2*max(background_i, 1) + readNoiseVariance) * (deadTimeCorrection/liveTimeSec)^2` with background, or `(max(counts_i, 1) + readNoiseVariance) * (deadTimeCorrection/liveTimeSec)^2` without background. Weight is `1/variance`.
5. Solve `beta = inverse(X^T W X) X^T W y`. Report coefficient order as `amplitude`, `tailAmplitude`, `background`, and `linearSlope`. `degreesOfFreedom = roi.count - 4`; `reducedChiSquare = sum(weight_i * residual_i^2) / degreesOfFreedom`; `covariance = inverse(X^T W X) * reducedChiSquare`.
6. Bootstrap intervals use the Mulberry32 generator listed under `GS-BS-0441`, a frozen calibrated design matrix, frozen weights, and residual resampling in corrected-rate space. The service does not use Poisson raw-count resampling for this endpoint. Percentiles use sorted samples with linear interpolation at probabilities `0.16`, `0.84`, `0.025`, and `0.975`.
7. Diagnostics use the same prepared fit and compute leverage from the weighted design hat matrix. Internally studentized residuals use `residual_i * sqrt(weight_i) / sqrt(max(1e-12, 1 - h_i))`. The `residualDiagnostics` object contains exactly `weightedMeanRate`, `weightedRmsRate`, `maxAbsInternallyStudentized`, `maxLeverage`, and `reviewThreshold`. `weightedMeanRate = sum(weight_i*residual_i)/sum(weight_i)` and `weightedRmsRate = sqrt(sum(weight_i*residual_i^2)/sum(weight_i))`; both are weighted residual metrics in corrected count-rate units. Residual review is required when `maxAbsInternallyStudentized > 2.8` or when `reducedChiSquare > 3.0`; the numeric `reviewThreshold` field remains `2.8` because it is the studentized-residual threshold, not the chi-square threshold.
8. Isotope screening fits each candidate isotope independently using the same preparation rules. Candidate AICc uses WLS weighted SSE, not unweighted residual SSE: `weightedSSE = sum(weight_i*residual_i^2) = reducedChiSquare*degreesOfFreedom`. AICc is `n*ln(max(weightedSSE/n, 1e-12)) + 2*k + (2*k*(k+1))/(n-k-1)` with `k=4` and `n=roi.count`. Rows are sorted by AICc and `deltaAicc` is relative to the best candidate.

## GS-CAL-0328 — Calibration file ownership and detector identity

The calibration file is a detector asset, not request data. The service must load `/app/data/calibration.gamma.json` once, validate the detector id, and reuse the parsed object for all routes. This rule was introduced after a strace review showed repeated `openat` calls around calibration loading during high-frequency bootstrap requests. Reusing the parsed calibration prevents descriptor churn and also ensures that `/fit`, `/batch-fit`, `/diagnostics`, and `/isotope-screen` apply identical channel-to-energy conversion.

The calibration record defines the Orion detector as `GS-ORION-17`; public route responses preserve that exact detector id. Route code may keep calibration helper functions wherever the project structure requires, but implementation evidence for this requirement is expected to point at `/app/src/calibration.ts` and the calibration data file itself. Compliance matrix `source` still cites this requirement ID in the methods bundle, not the implementation file.

## GS-NRM-0417 — Live-time normalization, dead-time convention, and background

The lab records counts during live acquisition time, while the wall-clock real time captures detector dead time. The API convention is explicit: `realTimeSec` must be greater than or equal to `liveTimeSec`, and both values are part of the physical request contract. `realTimeSec < liveTimeSec` is not a tolerable rounding case; it is a bad-timing request and returns HTTP 400 JSON.

Background subtraction is performed before dead-time division in the corrected-rate formula specified above. The background object is nested request data, not a response normalization field. The response indicates only whether background subtraction occurred and the scale factor used. This convention keeps API output stable while preserving enough information for reviewers to tell whether a background run contributed to the result. Implementation evidence for this requirement must include the legacy normalization module path `/app/src/normalization.ts`, which owns `deadTimeCorrection`, `backgroundScale`, corrected observed rates, and rate variances.

## GS-TAIL-0633 — Low-energy tail term

The Na-22 and mixed-card spectra used during the Orion audit show an asymmetric low-energy shoulder. A Gaussian-only model can look acceptable in a narrow plot but biases amplitude and background estimates. The service therefore uses a four-term model with the canonical term vocabulary `gaussian`, `lowEnergyTail`, `constant`, and `linear`, and route responses expose the same vocabulary through `modelTerms`.

The tail basis is one-sided: `lowEnergyTail = exp((E-center)/tailDecayKeV)` at or below the peak center and `0` above the center. It is not multiplied by the Gaussian column. The reported coefficient name is `tailAmplitude`. Alternative strings such as `exponential_tail`, `tail`, or `low_energy_tail` are not part of the wire contract because downstream report snapshots compare model terms by exact string identity.

## GS-WLS-0182 — Weighted least-squares fit and covariance

The fit is a weighted least-squares solve in calibrated energy space. The design matrix, variance formula, coefficient order, degrees of freedom, reduced chi-square, and covariance definitions are listed in the numerical block. The endpoint response exposes both the fitted curve (`fittedRates`) and point residuals (`residuals`) for `/fit` so reviewers can reproduce reduced chi-square and diagnostics from the response.

This requirement was added after a regression used channel index as the linear basis and reused raw-count variance after background subtraction. That bug produced similar peak centers in small examples but failed bootstrap reproducibility and diagnostics. Implementation evidence for this requirement normally includes `/app/src/fit.ts`, with matrix utilities cited separately when the solve is factored out.

## GS-BS-0441 — Deterministic bootstrap intervals

Bootstrap output is part of the API contract, so the pseudo-random generator must be fully specified. Given an unsigned 32-bit seed, Mulberry32 advances as follows: `t = seed += 0x6D2B79F5`; `t = Math.imul(t ^ (t >>> 15), t | 1)`; `t ^= t + Math.imul(t ^ (t >>> 7), t | 61)`; the next uniform value is `((t ^ (t >>> 14)) >>> 0) / 4294967296`. Seeds must be integers; non-integer seeds are request errors.

For each bootstrap replicate, resample residuals with replacement in corrected-rate space, add them to the original fitted rates, and solve with the same calibrated design matrix and the same frozen weights. The endpoint reports amplitude intervals only: `statistic: "amplitude"`, `pointEstimate`, and `confidence.ci68`/`confidence.ci95`. Using Poisson resampling of raw counts, changing weights per replicate, or using another PRNG violates this requirement even when interval widths appear plausible.

## GS-BAT-0726 — Sorted batch fitting and compact responses

Batch output is a reporting interface, not a dump of every route-internal vector. Runs are sorted lexicographically by `runId` and processed independently so that one background or live-time setting cannot leak into the next result. The envelope reports `detectorId`, `runCount`, `sortedBy: "runId"`, and `results`.

Compact result rows have a closed schema. With `includeResiduals` false or omitted, the only allowed row keys are `runId`, `roi`, `coefficients`, `normalization`, `reducedChiSquare`, and `qualityFlags`. The row must omit per-row `detectorId`, `isotope`, `method`, `weighting`, `calibrationApplied`, `modelTerms`, `covariance`, `degreesOfFreedom`, `residuals`, `fittedRates`, and nested `fit`. With `includeResiduals` true, the only additional allowed row keys are `residuals` and `fittedRates`. This closed field set was introduced because archived report snapshots rely on stable, compact batch output. A correct implementation may call the same internal fitting routine as `/fit`, but the batch wire shape remains distinct.

## GS-QC-0864 — Quality flags and review thresholds

Quality flags are exact string literals and exact ordering is part of the contract: `tail-model-applied`, `background-subtracted`, `dead-time-corrected`, `high-reduced-chi-square`. The dead-time flag applies when `deadTimeCorrection > 1.0005`. The high chi-square flag applies when `reducedChiSquare > 3.0`. The background flag applies only when a background object was accepted and used. The tail flag applies whenever the four-term tail-aware model is applied.

Diagnostics may append `residual-review` after the canonical fit flags. Do not sort flags alphabetically and do not deduplicate by converting through an unordered collection. The report generator preserves order because quality flags are meant to read like the analysis sequence: model choice, subtraction, timing correction, statistical review. Reduced chi-square uses the `> 3.0` threshold for the high-chi-square flag and for diagnostics review; the `2.8` value belongs only to internally studentized residual review.

## GS-DIAG-0911 — ROI residual diagnostics

Diagnostics are designed for reviewers who need to decide whether a suspicious fit should remain in an automated audit. The response repeats the detector id, request isotope, optional request run id, method name, top-level ROI, compact fit, integrals, residual diagnostics, decision, and quality flags. The `integrals` object is intentionally small and numeric: `observedRateSum`, `fittedRateSum`, and `absoluteResidualRateSum`. The absolute residual sum uses absolute values point by point and must not be replaced by a signed sum that can cancel around the peak.

The residual diagnostics object reports the leverage-aware residual review values defined in the numerical block. It explicitly includes `weightedMeanRate` and `weightedRmsRate` as weighted residual metrics: they are computed from point residuals using the same WLS weights as the fit, not from raw observed rates and not from unweighted residuals. `decision` is `review-required` if `maxAbsInternallyStudentized > 2.8` or `reducedChiSquare > 3.0`; otherwise it is `accepted`. The compact fit fields mirror the fit endpoint's coefficient names and statistical quantities but do not include the full fitted-rate and residual arrays.

## GS-SCR-1034 — Candidate isotope screen

The candidate screen is for triage, not final identification. Each candidate isotope is fitted independently with the same normalization and WLS rules. Candidate rows are sorted by AICc, carry one-based `rank`, and expose `deltaAicc` relative to the best candidate. The AICc score is based on weighted SSE from the WLS fit (`sum(weight_i*residual_i^2)`, equivalently `reducedChiSquare*degreesOfFreedom`), not the unweighted sum of squared residuals. Unknown candidate names are request errors because the screen cannot rank a source whose peak parameters are absent from the calibration table.

This endpoint exists because agents and humans both tend to reuse a single prepared ROI when comparing isotopes. That shortcut gives attractive numbers but is not the documented screen. The fit window and basis must follow each candidate's own peak definition before AICc ranking.

## GS-MTX-0550 — Compliance matrix and audit evidence

After patching the service, write `/app/output/compliance_matrix.json`. It is an object with top-level `task`, `auditCaptures`, and `entries`. `auditCaptures` is exactly the string array `[/app/audit/strace-gammaspec.log, /app/audit/lsof-gammaspec.txt]` using JSON strings with those absolute paths. Required entries are `GS-CAL-0328`, `GS-NRM-0417`, `GS-TAIL-0633`, `GS-WLS-0182`, `GS-BS-0441`, `GS-BAT-0726`, `GS-QC-0864`, `GS-DIAG-0911`, `GS-SCR-1034`, and `GS-MTX-0550`.

Each entry contains `requirementId`, `source`, `fixSummary`, `evidence`, and `verifiedBy`. `source` cites this methods bundle as `/app/docs/gammaspec_methods.md#<requirementId>`. `fixSummary` is a human-readable summary of at least five words. `evidence` and `verifiedBy` are non-empty arrays of absolute `/app/...` path strings. Implementation files belong in evidence and verifiedBy, not source. At minimum, `GS-NRM-0417` evidence and verifiedBy must include `/app/src/normalization.ts`; `GS-WLS-0182` includes `/app/src/fit.ts`; `GS-BS-0441` includes `/app/src/bootstrap.ts`; `GS-BAT-0726` includes `/app/src/batch.ts`; `GS-DIAG-0911` includes `/app/src/diagnostics.ts`; `GS-SCR-1034` includes `/app/src/screening.ts`; and `GS-CAL-0328` includes `/app/src/calibration.ts`.
