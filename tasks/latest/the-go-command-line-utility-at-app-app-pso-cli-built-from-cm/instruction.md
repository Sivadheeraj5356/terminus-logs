The Go command-line utility at `/app` (`/app/pso_cli` built from `./cmd/pso`) is a system administration utility designed for automated infrastructure configuration management and server parameter tuning across Linux clusters. Site reliability engineers (SREs) and system administrators invoke `/app/pso_cli` to tune multi-dimensional operating thresholds, service quotas, and kernel resource limits. The CLI evaluates candidate server configurations using an internal parameter evaluation engine (`/app/internal/pso/pso.go`). However, the current engine implementation fails to enforce several critical operating boundary invariants, parameter step constraints, and configuration history formatting rules required by the infrastructure management suite. **System Administration Operational & Behavioral Invariants:**
1. **Configuration Throttle Linear Decay (`w(t)`)**: Across configuration tuning steps `t` from `0` up to `max_iterations - 1`, the configuration step throttle `w(t)` must strictly follow a linear decay schedule from `w_start` down to `w_end`. The linear decay denominator must be `max_iterations - 1` (for `max_iterations > 1`), ensuring that `w(0)` exactly equals `w_start` and `w(max_iterations - 1)` exactly equals `w_end`.
2. **Independent Parameter Step Jitter Sampling (`r1`, `r2`)**: For every server configuration dimension, the random configuration step jitter multipliers (`r1` and `r2`) must be sampled independently using `rng.Float64()`. Specifically, when evaluating each parameter dimension, `r1` must be sampled independently prior to `r2` for that dimension.
3. **Parameter Adjustment Rate Clamping (`v_max`)**: Every dimension of a candidate server's adjustment rate (delta) must respect the absolute parameter step limit `v_max`. After a dimension's step adjustment is updated, if it is strictly greater than `v_max`, it must be clamped to `v_max`; if it is strictly less than `-v_max`, it must be clamped to `-v_max`.
4. **Service Boundary Constraints & Quota Rebound (`max_bound`, `min_bound`)**: Every dimension of a candidate configuration vector must remain within the valid server quota limits `[min_bound, max_bound]`. If a dimension's updated configuration value strictly exceeds `max_bound`, its value must be clamped to `max_bound` and its corresponding adjustment rate must undergo a quota rebound by multiplying by `-0.5`. Similarly, if a dimension's updated configuration value is strictly below `min_bound`, its value must be clamped to `min_bound` and its adjustment rate multiplied by `-0.5`. Exact equality at either boundary (`max_bound` or `min_bound`) is valid and does not trigger rebound.
5. **Configuration State Management (`NodeBest` and `ClusterGlobalBest`)**: Each candidate server configuration's local optimal state (`NodeBest`) and the entire cluster's global optimal state (`ClusterGlobalBest`) must be evaluated asynchronously immediately after all dimensions of the candidate state are updated during a configuration step (including the initial evaluation prior to step `0`).

   * If the candidate's metric is exactly equal to `best_val` (`val == best_val`), the infrastructure engine strictly prefers configurations nearer to the origin space: `best_position` must be updated to the candidate's configuration if and only if the Euclidean resource distance of the candidate's position is strictly less than the Euclidean resource distance of `best_position`. If the candidate's resource distance from the origin is equal to or greater than the existing optimal position's distance, the existing `best_position` must be retained.
6. **Output Schema & Monotonic History Filtering**: The JSON output written to the specified `--output` file must be a JSON dictionary object with exactly three top-level keys formatted in `snake_case`: `"best_position"` (an array of floats representing quota limits), `"best_value"` (a float representing the load metric), and `"history"` (an array of JSON objects logging the tuning sequence).
