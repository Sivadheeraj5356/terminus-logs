This is a security finding, not a routine bug report: chainaudit's tamper-evidence guarantee for the compliance event log has a detection bypass. Since last month's storage migration, verify can't reliably tell real tampering from harmless encoding differences — a checkpoint genuinely altered during the incident currently verifies as clean, while unrelated streams get flagged as corrupt, exactly the noise that trains people to ignore alerts that matter. Until this is closed, the tamper-evidence property this system exists to provide does not actually hold.

Two things, in order. First, prove the bypass is real: copy /app/data/chainaudit.db to /app/out/exploit.db, tamper with one event the way an attacker with database write access but no signing key actually could, and record what you changed in /app/out/exploit_report.json as {"stream_id": ..., "seq": ...}. Construct new tampering yourself against a stream that isn't already flagged, and patch the row's own stored hash to match your edit — a check that only catches unpatched tampering isn't proving much.

Second, close the bypass and the case that motivated it: fix cmd/chainaudit so verify and compact both behave correctly per the contract in /app/CHAINAUDIT-SPEC.md, including when fixed verify runs against your own exploit.db. compact has a related gap: it leaves data past its retention window in place, or prunes it so verify can't reconstruct integrity afterward, destroying evidence a legal hold exists to preserve. Signatures depend on the key-management sidecar at http://127.0.0.1:8500; some keys were rotated during the migration, and the code doesn't cleanly distinguish a revoked key from a forged signature.

Work against /app/data/chainaudit.db as-is — don't regenerate it. Outputs: chainaudit verify --db /app/data/chainaudit.db --out /app/out/verify_report.json, and chainaudit compact --db /app/data/chainaudit.db --out /app/out/compact_manifest.json --now-file /app/data/NOW.txt. Both must agree with each other and be safe to run more than once.
