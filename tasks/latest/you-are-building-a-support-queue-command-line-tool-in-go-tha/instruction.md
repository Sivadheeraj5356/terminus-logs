You are building a support-queue command line tool in Go that manages a SQLite database of support agents, tickets, resolutions, and an HMAC-secured audit chain. The binary lives at /app/app and every command takes the database path as its first argument, followed by any command-specific arguments. Full command signatures live in /docs/API_SPEC.md, the table layout is in /docs/schema.md, exact error strings are in /docs/error-codes.md, chain rules live in /docs/chain-spec.md, statistical formulas live in /docs/statistics-spec.md, and the integrity-check rules live in /docs/lint-spec.md. Treat those files as the source of truth for anything not covered here.

At a high level, init creates the four core tables and must be safe to run more than once. Add-agent and open-ticket insert rows and reject duplicates or bad tier or priority values with specific messages. List-tickets prints tickets sorted by priority urgency and age. Resolve-ticket closes a ticket, checks it against its SLA window, and appends an entry to the resolution_chain using HMAC-SHA256, with the signing key coming from the HMAC_SECRET environment variable or a documented fallback if unset. Chain-verify walks the chain looking for tampering, recomputing each row's hash from that row's own underlying field data (ticket_id, agent_id, resolution_minutes, sla_met, resolved_at, prev_hash, as stored in resolution_chain itself — chain-verify does not re-query the tickets or resolutions tables) rather than simply trusting the already-computed current_hash value that is stored alongside those fields. See chain-spec.md for the exact verification procedure.

The remaining commands turn stored data into reports: priority-report and agent-stats summarize SLA performance and each also carries one more computed field beyond the obvious counts (a margin figure and a digest, respectively, both described in API_SPEC.md), sla-report and priority-stats and ticket-analytics compute resolution-time statistics with rounding and variance conventions that must not be mixed up, and workload-balance shows how close each agent is to their tier's capacity. Read the docs closely since similar-looking commands use different formulas.

Two more commands round out the tool. dispersion-report computes a median and median-absolute-deviation view of resolution times; the median has to be derived with the same nearest-rank formula used for p50/p75/p95 elsewhere in this tool, not the textbook average-of-two-middle-values median, since the two disagree whenever there is an even number of resolutions. escalation-audit lists open tickets whose time-in-queue has breached a severity band relative to their SLA window, using one `datetime('now')` value captured up front and reused for every ticket rather than a fresh timestamp per row; its rows are sorted by severity band (most severe first), which is the opposite convention from priority-stats' alphabetical ordering, and each row also reports a ratio field that must be truncated toward zero to four decimal places rather than rounded, a third rounding convention alongside the HALF_UP and HALF_EVEN ones used elsewhere. See API_SPEC.md and statistics-spec.md for the exact thresholds and formulas for both commands.

Finally, queue-lint checks the database for data-integrity problems that no single other command catches on its own: agents over their tier capacity, tickets with a corrupted status value, ticket_ids resolved more than once, resolution rows left orphaned from their ticket, resolutions whose sla_met has drifted out of sync with a fresh recomputation off resolution_minutes and priority, and gaps in the resolution_chain's chain_id sequence. It always runs all six checks in a fixed order (never alphabetical), prints a pass or fail summary line per check followed by any violating identifiers, and finishes with an overall pass or fail line. See lint-spec.md for the exact rule order, identifiers, and output format.
