Beacon packets are a compact snapshot of what a field beacon reported at a point in time. Operators care about whether the packet can be trusted for routine monitoring, not about repairing the packet in place. The identity should be carried through exactly as received so a held packet can still be traced back to the source, but blank identities are not acceptable for release decisions. Sequence numbers represent normal forward reporting and should not look empty or reset. Drift is judged by distance from the expected position, so direction does not make an excessive movement safer. Battery and zone checks are profile-specific because each pier or watch area may use different operating limits.

A clear report means the packet satisfied every active policy for the selected profile. A held report means the packet was understood but at least one policy concern needs operator attention. When several concerns apply, the report should present the full set consistently so two reviewers comparing the same packet see the same result. The existing repository examples use the vocabulary that downstream field notebooks already expect, and that vocabulary should remain stable.

Command failures are different from packet holds. Missing command inputs, a profile name that the tool does not know, broken JSON, unreadable packet files, and unwritable report paths mean the inspection did not complete. In those cases, operators should see an error rather than a normal result, and automation should not find a leftover report file that looks like a completed inspection.
