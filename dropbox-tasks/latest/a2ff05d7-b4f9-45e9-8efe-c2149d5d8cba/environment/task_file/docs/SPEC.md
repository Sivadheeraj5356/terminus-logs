# GRUB Command-Line Rollout Contract

Selected config files are `/usr/lib/default/grub` and `/etc/default/grub`, applied in that order when present. Drop-ins are selected from `/etc/default/grub.d/`, must end in `.cfg`, and must not have a basename starting with `.`. Drop-ins are applied after main files by basename order. `EffectiveGrubConfig.source_order` lists selected paths in applied order.

Supported assignments are `GRUB_CMDLINE_LINUX`, `GRUB_CMDLINE_LINUX_DEFAULT`, `GRUB_DISABLE_OS_PROBER`, and `GRUB_DISTRIBUTOR`. Lines may start with `export `. Comments begin with `#` outside single or double quotes. Assignment values may be unquoted, single-quoted, or double-quoted; surrounding quotes are removed, spaces inside quotes are preserved, and comment markers inside quotes are literal. Empty command-line assignments reset that list to empty. Repeated supported assignments use the last value in applied order.

`GRUB_CMDLINE_LINUX` and `GRUB_CMDLINE_LINUX_DEFAULT` assignment values are command-line strings, not single tokens. After removing the assignment's surrounding quotes, split the resulting command-line string into tokens on whitespace outside quotes. Single and double quotes inside the command line preserve spaces within the quoted token and are removed. For example, `GRUB_CMDLINE_LINUX="audit=1 slab_nomerge"` produces `["audit=1", "slab_nomerge"]`, while a runtime string containing `'iommu=on'` produces the token `iommu=on`. A token's parameter key is the substring before the first `=`, or the whole token when no `=` is present. Effective rollout parameters are `cmdline_linux` followed by `cmdline_linux_default`.

`GRUB_DISABLE_OS_PROBER` accepts `true`, `yes`, `1`, `false`, `no`, and `0`, case-insensitively. Invalid values add global finding `bad-bool:<source>:GRUB_DISABLE_OS_PROBER:<value>`. If the final value is false, add global finding `os-prober-enabled`. `GRUB_DISTRIBUTOR` is reported as the final scalar value and has no findings.

Global findings also include `forbidden-param:<key>` for each effective parameter key listed in `policy.forbidden_params`, `missing-required-param:<key>` for each key in `policy.required_params` that is absent, and `missing-luks-param:<key>` for each key in `policy.required_luks_params` that is absent from the effective rollout parameters. Duplicate effective parameter keys emit `duplicate-param:<key>` once, except duplicate keys named `rd.luks.uuid` are allowed. Conflicting effective keys emit `conflict-param:<left>:<right>` once for the unordered pairs `quiet` with `debug`, `nomodeset` with `i915.modeset`, `intel_iommu` with `amd_iommu`, and `systemd.unified_cgroup_hierarchy` with `cgroup_no_v1`. Effective IOMMU parameters `intel_iommu`, `amd_iommu`, and `iommu` with values `off`, `pt`, `passthrough`, or `soft` emit `weak-iommu-setting:<key>:<value>` in global lexicographic order with other global findings.

Each `HostAudit.hostname` is copied from the input `HostState.hostname`. Per host, blockers are emitted first in this order: `unsupported-bootloader:<hostname>:<bootloader>` when `bootloader` is not `grub`; `kernel-too-old:<hostname>:<kernel_version>` when the numeric kernel version is below `policy.min_kernel_version`; `secure-boot-disabled:<hostname>` when required by policy; `lockdown-disabled:<hostname>` when required by policy; `iommu-missing:<hostname>:<iommu_key>` when required by policy and neither runtime nor effective parameters include the architecture-appropriate IOMMU key; `runtime-weak-iommu:<hostname>:<key>:<value>` for each runtime IOMMU parameter with value `off`, `pt`, `passthrough`, or `soft`, in runtime order; `runtime-missing-param:<hostname>:<key>` for each effective key absent at runtime in effective key order; `runtime-value-drift:<hostname>:<key>:<expected>:<actual>` for each effective `key=value` parameter whose key is present at runtime but whose last runtime value differs from the last effective value for that key, excluding `rd.luks.uuid`; `runtime-duplicate-param:<hostname>:<key>` once per duplicated runtime key in first duplicate encounter order, excluding `rd.luks.uuid`; `runtime-init-override:<hostname>:<value>` for each runtime `init=<value>` whose value is not `/sbin/init`, in runtime order; `runtime-forbidden-param:<hostname>:<key>` for each forbidden runtime key in runtime order; `encrypted-root-missing:<hostname>:<key>` for each required LUKS key absent at runtime on encrypted-root hosts; `encrypted-root-no-tpm2:<hostname>` when an encrypted-root host is under a policy requiring Secure Boot but reports `tpm2=false`; and `unsigned-module:<hostname>:<module>` for each loaded module that is neither builtin nor signed when Secure Boot is required. For IOMMU host checks, use `amd_iommu` when `HostState.arch` contains `amd` case-insensitively, use `intel_iommu` when it contains `x86_64` or `intel` case-insensitively and does not match the AMD rule, and use `iommu` otherwise. The IOMMU key is always part of the `iommu-missing` string; `iommu-missing:<hostname>` is not a valid finding. A weak IOMMU value still counts as a present key for the `iommu-missing` check; weak values are reported by the weak-IOMMU finding families.

Runtime parameters are parsed with the same command-line token rules as effective parameters. Host warnings are emitted after blockers in this order: `rootfs-risk:<hostname>:<root_fs>` when `root_fs` is `nfs`, `iscsi`, or `tmpfs`; then `debug-param-active:<hostname>:<key>` for each runtime debug parameter not listed in `policy.allowed_debug_params`, in runtime order. Debug parameter keys are `debug`, `initcall_debug`, `ignore_loglevel`, `systemd.log_level`, and `drm.debug`.

Kernel-version comparisons use the numeric components in order and ignore non-numeric suffix text. Missing numeric components compare as zero, so `5.10.42-custom` is below `5.15.0`, `5.15.0` is equal to `5.15.0`, and `6.1.12` is above `5.15.0`.

`AuditReport::rollout_summary()` derives an aggregate summary from the report without re-reading files or hosts. `host_count` is `hosts.len()`. `blocked_hosts` contains hostnames whose `blockers` list is non-empty, in report host order. `warning_hosts` contains hostnames with no blockers and at least one warning, in report host order. `clean_hosts` contains hostnames with no blockers and no warnings, in report host order. `blocker_count_by_host` includes every host with at least one blocker and maps hostname to blocker count. `warning_count_by_host` includes every host with at least one warning and maps hostname to warning count.

`top_finding_codes` is computed from `finding_count_by_code`, sorted by descending count and then lexicographic code, and contains at most the first five entries. `effective_param_keys` is the list of unique effective parameter keys from `cmdline_linux` followed by `cmdline_linux_default`, in first-seen order. `required_runtime_coverage` has one entry for each effective parameter key. Its value is the number of hosts whose runtime state is not flagged with `runtime-missing-param:<hostname>:<key>` and is not flagged with `runtime-value-drift:<hostname>:<key>:`. A host with a blocker or warning unrelated to that key can still count as covered for that key. `rollout_ready` is true only when `global_findings` is empty and every host has empty blockers and warnings.

`AuditReport::remediation_plan()` converts global findings, host blockers, and host warnings into deduplicated remediation actions. Each action has `priority`, `code`, `detail`, and `targets`. The finding code is the substring before the first `:`. For global findings, the target is `"global"` and the detail is the substring after the first `:`, or the empty string when the finding has no `:`. For host blockers and warnings, the target is the host name from `HostAudit.hostname`; the detail is the substring after `<code>:<hostname>:`, or the empty string when the finding has no detail after the hostname. Actions are grouped by `(priority, code, detail)`. Targets inside an action are unique and ordered as `"global"` first if present, followed by hosts in `AuditReport.hosts` order.

Priority is assigned by code. Priority `0`: `unsupported-bootloader`, `kernel-too-old`, `secure-boot-disabled`, `lockdown-disabled`, `encrypted-root-no-tpm2`, `unsigned-module`, `runtime-init-override`, `runtime-forbidden-param`, `forbidden-param`, and `bad-bool`. Priority `1`: `missing-required-param`, `missing-luks-param`, `encrypted-root-missing`, `iommu-missing`, `weak-iommu-setting`, `runtime-weak-iommu`, `runtime-missing-param`, and `runtime-value-drift`. Priority `2`: `duplicate-param`, `runtime-duplicate-param`, `conflict-param`, and `os-prober-enabled`. Priority `3`: `rootfs-risk` and `debug-param-active`. Any unknown code uses priority `4`. Return actions sorted by ascending priority, then lexicographic code, then lexicographic detail.

`AuditReport::staged_rollout_waves(max_wave_size)` builds deterministic deployment waves from the finished report. Hosts with one or more blockers are excluded from all waves. Remaining hosts are ordered by warning count ascending, then by original report host order. `max_wave_size == 0` is treated as `1`. Split the ordered hosts into consecutive waves of at most `max_wave_size` hosts. Wave names are `wave-1`, `wave-2`, and so on.

Each wave's `risk_score` is `global_findings.len() + sum(warning_count for hosts in the wave)`. Each wave's `required_actions` is derived from `remediation_plan()`: include an action if its targets contain `"global"` or any host in the wave. Format each included action as `<priority>:<code>:<detail>:<targets>`, where `<targets>` is the comma-separated intersection of that action's targets with `"global"` plus the wave hosts, preserving the target order from the action. Use an empty `<detail>` field as an empty string, so `os-prober-enabled` with global target formats as `2:os-prober-enabled::global`. Preserve remediation-plan order in `required_actions`. If every host is blocked, return an empty vector.
