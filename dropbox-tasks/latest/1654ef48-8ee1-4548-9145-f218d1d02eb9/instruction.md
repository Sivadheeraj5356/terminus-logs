We need a native security audit tool for a small infrastructure repo. Write a C program, build a compiled executable named `policy-auditor`, and use it to scan `/app/task_file/input_data/repo/` for risky production access policies; the default output must be `/app/task_file/output_data/findings.sarif`, and the executable must also support `policy-auditor <repo_dir> <sarif_output>`. Successful runs must return exit code 0 and write nothing to stderr.

The output is exact-match SARIF 2.1.0 shape: top-level `version` is `2.1.0`, `$schema` is `https://json.schemastore.org/sarif-2.1.0.json`, `runs[0].tool.driver.name` is non-empty, `runs[0].tool.driver.rules` is non-empty, and each result has `ruleId`, `message.text`, `locations[0].physicalLocation.artifactLocation.uri` as a path relative to the scanned repo with no leading slash, and `locations[0].physicalLocation.region.startLine` as a 1-based integer. Report every applicable risky line; rules are additive and do not short-circuit when a file has multiple issues. Do not modify any input file.

Only production-bearing policy files should be reported: `/app/task_file/input_data/repo/infra/terraform/prod/`, `/app/task_file/input_data/repo/k8s/prod/`, `/app/task_file/input_data/repo/infra/iam/*.json`, production deployment workflows under `/app/task_file/input_data/repo/.github/workflows/`, and production/deploy shell scripts under `/app/task_file/input_data/repo/scripts/`. A workflow is production-bearing when its path, filename, or top-level `name:` content indicates deploy/production, or when the workflow content includes `environment: production`. A shell script under `/app/task_file/input_data/repo/scripts/` is production-bearing when its path indicates prod, production, or deploy. Ignore docs, examples, dev/test/sandbox paths, placeholders, and binary/media assets. Report `SEC-PUBLIC-ADMIN` for public `0.0.0.0/0` or `::/0` ingress whose port or range includes 22, 3389, 5432, 3306, 6379, 9200, or 9300; Terraform ingress may appear as an `ingress { ... }` block, an `aws_security_group_rule`, or an `aws_vpc_security_group_ingress_rule`, and public CIDR fields include `cidr_blocks`, `cidr_ipv6_blocks`, `cidr_ipv4`, and `cidr_ipv6`. Do not report egress-only Terraform rule resources for this rule. The reported line for this rule is the line containing the public CIDR field or value, not the `from_port` or `to_port` line. Report `SEC-IAM-WILDCARD` for Allow statements with wildcard or privilege-management actions such as `*`, `iam:*`, `kms:*`, `s3:*`, `ec2:*`, `organizations:*`, `iam:PassRole`, or `sts:AssumeRole` when the same statement also uses resource `*`; emit one finding for each privileged action line, and handle simple IAM JSON documents, compact inline syntax, HCL arrays, and files without a top-level `Version` field. Do not report Deny statements for `SEC-IAM-WILDCARD`. Report `SEC-K8S-PRIVILEGED` for production Kubernetes `privileged: true` or `allowPrivilegeEscalation: true`; report `SEC-K8S-HOST-ACCESS` for production `hostNetwork`, `hostPID`, `hostIPC`, or `hostPath`; report `SEC-CI-DEPLOY-WRITE` for production deployment workflows using `pull_request_target` or `permissions: write-all`; report `SEC-UNPINNED-ACTION` for production deployment workflow `uses:` actions missing `@` or using refs such as `@main`, `@master`, or semantic tags instead of a 40-character commit SHA; report `SEC-SHELL-CURL-EXEC` for production/deploy scripts that pipe `curl` or `wget` output into `sh`, `bash`, `/bin/sh`, `/bin/bash`, or `sudo` variants of those shells. The same scanner must handle equivalent Terraform, IAM JSON/HCL, Kubernetes YAML, workflow YAML, and shell-script shapes when copied inputs are changed. Findings are scored by `ruleId`, relative path, and line number with a +/-1 line tolerance; false positives reduce precision, missed findings reduce recall, and the passing F1 threshold is 0.93. The C implementation must do the scan itself and must not shell out, spawn helper programs, or delegate work to another scanner.
