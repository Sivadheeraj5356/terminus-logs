Harden the bastion authentication policy under `/app/task_file/etc` so it is safe to promote to the real jump hosts. Work only by updating the listed configuration files in place.

The target files are `/app/task_file/etc/pam.d/sshd`, `/app/task_file/etc/pam.d/sudo`, `/app/task_file/etc/pam.d/ci-deploy`, `/app/task_file/etc/security/access.conf`, `/app/task_file/etc/security/time.conf`, `/app/task_file/etc/security/faillock.conf`, `/app/task_file/etc/ssh/sshd_config`, and `/app/task_file/etc/sudoers.d/bastion`.

Required policy:

- SSH must use PAM, disable password-only logins, disable root login, require public key plus keyboard-interactive PAM, and allow only `vpn`, `ops`, `breakglass`, and `ci` groups.
- `sshd`, `sudo`, and `ci-deploy` PAM stacks must enforce `pam_faillock` with `deny=3`, `fail_interval=900`, and `unlock_time=900`. Each stack needs preauth, authfail, and authsucc handling.
- `sshd` and `sudo` must require `pam_unix`, `pam_access`, and `pam_time`. In the `sshd` stack, the `pam_unix.so`, `pam_access.so`, and `pam_time.so` checks must be `auth` entries in that order and must precede the breakglass check. `sudo` must also contain an `account` entry using `pam_succeed_if.so ... user ingroup sudo`, and that group check must appear before `account required pam_unix.so` so group membership is checked before account success.
- `sshd` must require `pam_google_authenticator.so` MFA for normal VPN users. Members of `breakglass` may skip only that one MFA entry, and only after the preceding `pam_unix`, `pam_access`, and `pam_time` checks. Put `[success=1 default=ignore] pam_succeed_if.so ... user ingroup breakglass` immediately before the MFA entry; do not let the bypass skip any other check.
- `ci-deploy` must be usable only by members of `ci` from `10.20.0.0/16`, with no root login and no weekend access. Enforce the root denial in both the `auth` and `account` stacks with `pam_succeed_if.so ... user != root` before the `ci` group check. In the `auth` stack, the ordered checks must be faillock preauth, root denial, `ci` group check, `pam_access`, `pam_time`, faillock authfail, and faillock authsucc. Its stack must not contain `pam_permit.so`, even as a fallback or stack terminator.
- `access.conf` must first deny the exact group principal `(contractor)` (singular) everywhere, then deny all users from `203.0.113.0/24`, allow breakglass users from `*.corp.example`, deny breakglass users from every other origin, allow VPN users from `10.10.0.0/16`, allow ops users from `10.30.0.0/16`, allow CI users from `10.20.0.0/16`, and deny everything else. The breakglass deny rule must come before the VPN, ops, and CI allowance rules so a breakglass user who is also in another allowed group cannot fall through to those network allowances. First matching access rule wins.
- `time.conf` must allow breakglass SSH at all times, deny VPN SSH on Friday from 17:00 through 17:59 before the broader VPN allowance, allow VPN SSH only Monday-Friday from 06:00 through 21:59, allow ops SSH only Tuesday and Thursday from 10:00 through 15:59, deny CI deploy on Tuesday from 03:00 through 03:59 before the broader CI deploy allowance, allow CI deploy Monday-Friday, deny sudo for `sudo` users on Saturday and Sunday, and allow sudo for `sudo` users Monday-Friday. Do not add an `sshd` time allowance for CI-only users; CI access is service-specific to `ci-deploy`. Spell Monday-Friday as the concatenated token `MoTuWeThFr` (not `Wk` or another alias), and place each narrow denial before the broader allowance it constrains. First matching time rule wins.
- `faillock.conf` must set `deny = 3`, `fail_interval = 900`, `unlock_time = 900`, `even_deny_root`, and `audit`.
- `sudoers.d/bastion` must require `use_pty`, `log_input`, `log_output`, and `timestamp_timeout=0`. `%sudo` may run normal sudo commands, but no entry may use `NOPASSWD`. `%breakglass` may run only `/usr/bin/systemctl status *` and `/usr/bin/journalctl *`.

Use the existing file formats. For `access.conf`, group principals are written as `(group)`, and host suffix patterns such as `*.corp.example` are valid origins. For `time.conf`, use `service;tty;principal;times`, group principals as `(group)`, only the two-character weekday tokens `Mo Tu We Th Fr Sa Su Al`, and 24-hour ranges such as `0600-2200`. Concatenate multiple day tokens without separators, for example `MoTuWeThFr0600-2200`; shorthand aliases such as `Wk` are not part of this task's format. Prefix a time expression with `!` for a denial rule: if the negated expression matches, access is denied; if it does not match, evaluation continues to later rules. Lines are evaluated in file order for this task.
