Administrative commands and daemon request format

This document is part of the service specification in /app/SPEC.md. It defines the administrative commands installed on the system path and the daemon request format they drive. The host administration contract, the pools, hardening, log rotation, the scheduled jobs, and the command privilege rules are in /app/SPEC.md.

Administrative commands on the system path

dhcpdctl runs one JSON request document named on its command line through the daemon and prints the JSON reply. dhcpd-provision reconciles the pools in the database to exactly the set declared by the pool files, creating a newly declared pool, updating a pool whose lease time changed, and removing a pool together with its reservations, leases, and declines once it is no longer declared. It is idempotent, so running it again with the declarations unchanged makes no change and never duplicates a pool. It refuses to create a declared pool whose address range overlaps a pool already kept, leaving the existing pool intact and exiting non zero. Concurrent runs serialise so they never race into a duplicate or partial write. Run with the flag --check it makes no change and exits zero when the live pools already match the declared set and non zero on drift. It validates every declared pool file before touching the database, and a single malformed declaration aborts the whole run non zero with no partial changes. dhcpd-check validates the deployment, confirming the configuration file declares every required key and that every pool file is valid with a well formed address range and a positive lease time, exiting zero when all are valid and non zero, naming the offender, otherwise. dhcpd-fsck checks the database integrity and that the schema tables are present, exiting zero on a sound database and non zero on a corrupt or unreadable one. dhcpd-reap deletes every lease whose expiry is at or before the current time. dhcpd-backup writes a consistent snapshot of the database into the backup directory as a distinctly named SQL text dump for every invocation, a file whose name ends in .sql that is produced by dumping the database so that it carries the CREATE TABLE statements, with mode 0600, alongside a companion checksum file that holds only the bare sixty four character hex digest of the dump, prints the path of the dump, creates the backup directory with mode 0700 if it is absent, and keeps only the newest dumps up to the retention limit, which is DHCPD_BACKUP_KEEP taken from the environment when it is set, otherwise BACKUP_KEEP from the configuration, and seven when neither is set, pruning older dumps together with their checksum files. dhcpd-restore rebuilds the database from a dump written by dhcpd-backup, but first verifies the dump against its companion checksum and refuses, exiting non zero and leaving the database unchanged, when they do not match, and before it overwrites a valid restore it writes a pre restore safety snapshot of the current database into the backup directory, itself a SQL text dump whose name begins with pre-restore- and ends in .sql, with its own checksum. dhcpd-report prints one JSON object per pool ordered by pool id, each with the fields pool_id, cidr, total, active, available, and utilization, where utilization is the integer percentage of active over total. The reaper, the report, and the status request honour a current time override given in milliseconds through DHCPD_NOW_MS.

Advanced maintenance commands

dhcpd-renumber takes an existing pool CIDR and a new CIDR and moves the pool to the new range in a single transaction. Every reservation, lease, and decline of the pool keeps its offset from the network address, so an address at offset k in the old range moves to offset k in the new range; any that would land on the new network or broadcast address, or outside the new range when the new range is smaller, is dropped. It refuses, changing nothing and exiting non zero, when the new range overlaps a different existing pool, when the old pool is not present, or when either CIDR is malformed. Renumbering a pool to its own current CIDR is a no op. Concurrent runs serialise with the provisioner, and the run is recorded in the admin audit log.

dhcpd-audit reconciles the live tables against the pool ranges and reservations and prints one JSON object per pool ordered by pool id, each with the fields pool_id, cidr, lease_out_of_range, lease_on_exclusion, lease_on_decline, lease_wrong_client, and resv_out_of_range, counting respectively the leases whose address is outside the pool usable range, the leases sitting on an address string exclusion, the leases sitting on a declined address, the leases holding a client bound reservation registered to a different client, and the reservations outside the usable range. It then prints a final object with the fields orphan_leases, orphan_reservations, and inconsistencies, the last being the total across every pool and the orphans, where an orphan is a lease or reservation whose pool no longer exists. Without the --strict flag it always exits zero; with the --strict flag it exits non zero when the total number of inconsistencies is greater than zero and zero otherwise.

dhcpd-verify prints a canonical, signed manifest of the live database state so a deployment can be attested and compared byte for byte. The manifest is a sequence of lines each ending in a newline, in this order: one line, POOL then the CIDR then the lease seconds, for every pool ordered by network address; then one line, RESV then the pool CIDR then the address then the client, for every reservation ordered by pool network then address then client, where the address is written as an unsigned thirty two bit integer and an address string exclusion whose client is empty is written as a single dash; then one line, LEASE then the pool CIDR then the address then the client then the expiry then the state, for every lease ordered by pool network then address; then one line, DECLINE then the pool CIDR then the address, for every decline ordered by pool network then address. The final line is TAG then a space then the lowercase hex HMAC-SHA-256 of all of the preceding manifest bytes under the key that is the raw thirty two byte SHA-256 digest of the ASCII text dhcpd-verify-v1. It reads the database named by DHCPD_DB and exits zero.

Daemon request format

Each request is a JSON object with an op field, and each reply is a JSON object with a numeric code field and operation specific fields. create_pool takes cidr, lease_secs, and an optional reserved list whose entries are either an address string withheld from allocation or an object with ip and client_id that reserves an address for one client, and replies with code 201 and pool_id, or code 400 on bad input. lease takes pool_id, client_id, and an optional requested_ip, and offers the client reserved address if there is one, otherwise the requested address if it is free, otherwise the client previous address, otherwise the lowest free usable address, replying with code 200 and the ip and expires_ms, or code 409 when the requested address is held by another client, code 409 when the pool is exhausted, code 404 for an unknown pool, and code 400 when client_id is missing. renew takes ip and client_id and extends the lease. release takes ip and frees the address. decline takes ip and marks the address unusable. status takes pool_id and reports total, active, available, excluded, declined, and the active leases. The network and broadcast addresses of a pool are never allocated, a lease whose expiry has passed is reclaimed automatically, a current time in milliseconds may be supplied per request through a now_ms field, and a client bound reservation is not counted in the excluded total while an address string exclusion is.
