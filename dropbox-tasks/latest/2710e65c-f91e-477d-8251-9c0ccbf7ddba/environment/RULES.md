# Resolution and build contract

This document is the contract for the registry under /app/registry, the manifest at /app/manifest.toml, and the Go project scaffold at /app/project; a correct submission resolves a dependency set that satisfies every rule below, writes it as the lockfile described here, and supplies whatever compatibility code that resolution requires so the project at /app/project builds and behaves as specified. The illustrative registry in /app/docs/registry-format.md uses package names that do not appear anywhere under /app/registry; treat it only as a description of the file shapes, not as a hint about the real graph.

R1. Version triples. Every package version is a major.minor.patch triple of non-negative integers, no two versions of the same package are equal, and every comparison between two versions of the same package is decided by comparing major, then minor, then patch, as plain integers.

R2. Range operators. A dependency range names one operator and one version X.Y.Z: "=X.Y.Z" matches only that exact version; ">=X.Y.Z" matches any version whose (major, minor, patch) triple is greater than or equal to X.Y.Z under the comparison in R1; "^X.Y.Z" matches any version whose minor equals Y and whose major is greater than or equal to X, with no constraint on patch at all.

R3. Requirements, alternatives, conflicts. Each entry in a version's requires list is either a plain requirement written {"package": P, "range": G}, satisfied when P is present in the resolved set at a version matching G, or an alternative group written {"any_of": [...]} of plain requirements, satisfied when at least one listed alternative is satisfied; conflicts entries use the same {"package": P, "range": G} shape and forbid P at a version matching G from appearing in the resolved set together with the package that declares the conflict, and this prohibition holds regardless of which of the two packages' index.json carries the declaration.

R4. Reachable closure. Start from the root requirements listed in /app/manifest.toml, and for every package added to the resolved set follow the requires list of the one version chosen for it; the resolved set MUST equal exactly the packages reachable this way, so a package with no path back to a root requirement through chosen versions MUST NOT appear, and a package reachable this way MUST appear.

R5. One version per package. The resolved set assigns each package name at most one version, and every requirement, alternative, and conflict that names that package is evaluated only against that one chosen version, never against any other version the registry happens to offer.

R6. Lockfile shape. Write the resolved set to /app/out/lock.json as a single JSON object whose keys are the included package names and whose values are their chosen version strings, with no other keys and no nesting.

R7. Compatibility package. /app/project/consumer.go is fixed and imports fleetmesh/compat/telemetrybusv1; write the source for that import path under /app/project/compat/telemetrybusv1/ so it exposes whatever consumer.go calls, implemented against the telemetrybus version your lockfile resolves, matching the behavior documented in that version's registry stub and, when the version ships one, its MIGRATION.md.

R8. Build and standard library only. Once the lockfile and the compat package are in place, running "go build ./..." from /app/project MUST succeed using only the Go standard library, the fleetmesh/compat/telemetrybusv1 package you write, and the telemetrybus source at the resolved version, with no network access and no module outside this tree; the build always makes the resolved telemetrybus version available at the module path fleetmesh/telemetrybus at the tree root, so the compat package imports it directly from there, and no other copy of telemetrybus source belongs anywhere else under /app/project.

R9. Fixed inputs stay fixed. /app/registry, /app/manifest.toml, and /app/project/consumer.go are read-only reference material; solve the task by adding your own resolver, lockfile, and compat package under /app/project/compat/, and do not modify any of these three or add files anywhere else under /app/registry.

R10. Deterministic output. Applying R1-R5 always reaches the same set of package-version pairs regardless of what order a resolver considers packages in, so a resolution is not a matter of taste; write /app/out/lock.json with its keys in ascending lexicographic order by package name, so the file's own text carries no incidental ordering choice on top of the resolution itself.

R11. Runnable resolver. Add a Go source file at /app/project/resolver/main.go; once built from /app/project with "go build ./resolver", the resulting program MUST accept three positional arguments, a registry directory, a manifest file path, and an output path, in that order, and it MUST perform the resolution described in R1-R6 against whatever registry and manifest it is given, writing the result to the given output path in the shape R6 describes. It MUST NOT special-case any package name, version string, or path that appears only in the registry and manifest shipped under /app: the same built program is invoked again against those exact inputs and separately against a different registry/manifest pair it has never seen.
