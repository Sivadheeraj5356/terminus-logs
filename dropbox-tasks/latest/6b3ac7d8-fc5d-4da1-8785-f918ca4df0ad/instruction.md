Our `vaultseal` crypto harness gets fuzzed every night and spits out a pile of gdb backtraces and valgrind memcheck logs, and a Terraform module in `/app/triage` turns that corpus into a single deterministic `triage_report.json` — classifying each crash, scrubbing key material, correlating the gdb and valgrind sides, clustering near-identical crashes, and failing `terraform apply` when anything trips the severity gate. It was passing its acceptance suite until yesterday's refactor. It still runs end to end and still writes a report, but the report is now wrong in several places: the refactor introduced regressions in the analysis logic, and they don't all show up on the small sample corpus, so a quick run can look fine while the module is still broken.

You have a reference build of the engine — the way it behaved before the refactor — shipped as an opaque binary at `/app/oracle`. You can run it on any corpus you like:

```
/app/oracle --corpus-dir <dir> [--severity-gate high] [--redaction-salt vaultseal]
```

and it prints the canonical `triage_report.json` for that corpus to stdout. Its output is, by definition, correct. You cannot read its source — treat it as a black box and learn its behavior by running it.

Your job is to fix `/app/triage/scripts/analyze.py` so the module reproduces the oracle exactly: for any corpus, the module's `triage_report.json` must be byte-for-byte identical to what `/app/oracle` produces for that same corpus, salt, and gate. `/app/docs/TRIAGE_RUNBOOK.md` describes the pipeline's shape, the input log formats, the output contract, and the invariants, but it intentionally leaves the exact rules — the severity matrix, the clustering similarity threshold, the error-class precedence, the operation and key tie-breaks, the gate comparison — undefined. Those are whatever the oracle does; where the runbook is general, pin the behavior down empirically by constructing small corpora, running the oracle, and comparing. The sample corpus in `/app/corpus` is small and does not exercise every rule, and on it the current module happens to agree with the oracle, so a passing-looking sample run tells you nothing — you have to probe the rules the sample doesn't reach.

Some ground rules. Fix the analysis logic in `analyze.py` itself; do not have the module shell out to, import, or otherwise delegate to `/app/oracle` (or any other external process) — that is not a solution, and it will be rejected. Do not rewrite the module from scratch: the Terraform wiring, the on-disk encodings (the `vsk1:`/`vsx1:` redaction tokens, the `clu:` cluster ids), and the JSON shape (sorted keys, two-space indentation, trailing newline, findings ordered by severity then case id) are established, correct behavior — preserve them exactly, or the report will stop being byte-for-byte reproducible, and a from-scratch reimplementation will not reproduce the exact tokens and ids the report is expected to contain.

A few environment facts. Everything runs with no network access and the providers are already mirrored locally, so `terraform init` works offline — don't add providers or reach out. Correctness has to hold at scale: a real nightly run is not a handful of crashes but tens of thousands of them, and the analysis has to finish in well under a minute on a single core, so the clustering must stay near-linear — the naive all-pairs approach is too slow and won't come back in time. Applying the module against a corpus whose report is gated must still fail the apply while writing the report first. There's a bash harness under `/app/integration` you can use to run the module against the sample corpus while you work.
