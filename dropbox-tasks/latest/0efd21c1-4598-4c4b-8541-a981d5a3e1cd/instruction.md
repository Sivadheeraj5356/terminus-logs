Write a Go program, compiled to /app/hmm, that replays and analyses the duration-explicit recording process described by the cases in /app/data/cases.txt. Each case gives model parameters and a 64-bit seed but no recording. Your program has to produce three things per case, written one case at a time in input order to /app/output/results.txt at full double precision. First the exact recording the reference process emits for that seed, entry for entry. Then the log-likelihood of that recording under the model, treating the seed as unknown. Then the expected number of visits the window intersects given the recording. It should also take an input path and an output path as command-line arguments so it can run on other case files. With no arguments it uses those two defaults. Use only the Go standard library and do the work in the compiled binary, no shelling out to Python or anything else.

The hard part is that the docs alone are not enough. /app/docs/hmm-spec.md pins the model family, the splitmix64 stream, the categorical scan rule, the visit-boundary draws, the whole recording layer, the schemas, the tolerances, and even how many draws the window opening consumes. What it deliberately does not document is the law behind that opening. The recording starts on a visit already in progress, and the distribution governing that visit's age and total length is left to discovery. The probe reference at /app/ref is the authority on it. It answers any case file in the same format at full precision but refuses anything longer than 128 steps, and the graded cases run to several thousand, so you cannot wrap it or copy it. Design small probe cases, run it, pin down the exact semantics, then implement them yourself for any length. Budget your time here. A compiled solver built on your best current hypothesis and refined against the reference's answers beats probing until you are certain. Getting a single convention wrong desyncs the whole recording. On top of that the likelihood on the long cases underflows to zero if you multiply raw probabilities, so that part has to be done in a numerically stable way.

The grader also runs your binary on freshly generated cases with unseen parameters and seeds, so it has to work for any input in this format, deterministically, not just the shipped file.
