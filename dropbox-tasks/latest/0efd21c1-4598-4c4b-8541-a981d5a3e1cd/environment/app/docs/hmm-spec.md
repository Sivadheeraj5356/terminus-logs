# Inference contract: replaying and analysing a duration-explicit recording process

This is the binding contract the solver at `/app/hmm` must satisfy. It fixes the model family, the pseudo-random stream, the quantities to compute, the input and output schema, the invocation, and the match tolerance against a hidden reference. Part of the semantics is deliberately specified by the probe reference at `/app/ref` rather than by this document; see "What the reference defines" below. How to compute the quantities exactly is the task.

## Model family

Each case describes a hidden state process observed through a recording window of exactly `T` steps. The state process is built from visits with explicit dwell-time distributions; the window is a finite excerpt of it. The case carries no recording: the recording is produced by the process itself, deterministically, from the case's `SEED`, and reproducing it exactly is part of the task.

The parameters are `N` hidden states, `K` observation symbols, a dwell cap `Dmax`, a 64-bit `SEED`, and:

- `pi` — a length-`N` probability vector: the distribution of the state the window opens in, `P(z_1 = i) = pi_i`.
- `A` — an `N x N` jump matrix. `A_ij` is the probability that the visit after a visit to state `i` is to state `j`. Every diagonal entry `A_ii` is zero (a jump always changes state) and each row sums to 1.
- `B` — the `N x K` emission matrix; `B_i(k)` is the probability that an entry generated by state `i` shows symbol `k`, given it is not missing. Each row sums to 1.
- `D` — the `N x Dmax` duration matrix. `D_i(d)` is the probability that a visit to state `i` lasts exactly `d` steps, for `d = 1..Dmax`. Each row sums to 1. Rows may contain zeros — a state can have a minimum duration, a maximum below `Dmax`, or any shape in between. `Dmax` can be 1, and can exceed `T`.
- `M` — a length-`N` vector of missingness parameters in `[0, 1)`, one per state. They govern how entries go missing; exactly how is part of the reference semantics.

Visits run consecutively: a visit to state `i` lasts `d ~ D_i` steps, and when it ends the next visit's state is drawn from row `i` of `A`, its duration from that state's `D` row, and so on. The per-step state `z_t` is the state of the visit covering step `t`. The window opens on a visit already in progress and closes at step `T` whether or not the visit in progress is complete: for the likelihood, the final visit contributes the survivor mass `sum_{d>=u} D_i(d)` for the `u` steps it covers inside the window, not the pmf value. At each step the recording either shows a symbol or the missing mark `?`.

## The recording layer

The recording apparatus is fully documented. The entry recorded at step `t` is generated by the state at step `t-1` for `t >= 2`, and by the state at step 1 for `t = 1` — the apparatus lags one step behind the process. For each step, in order: first a symbol draw is taken, always, from the `B` row of the generating state `s`; then a masking draw is taken, and the entry is `?` iff that uniform is `< m_s` of the same generating state. A masked entry still consumed its symbol draw; the drawn symbol is discarded. In the likelihood, a `?` at a step generated by state `s` contributes the factor `m_s` and a recorded symbol `k` the factor `(1 - m_s) * B_s(k)`.

## The pseudo-random stream

All randomness in the process derives from one splitmix64 stream, seeded with the case's `SEED` as an unsigned 64-bit integer. One step of the stream, on unsigned 64-bit state `z` with wrapping arithmetic:

```
z += 0x9E3779B97F4A7C15
x = z
x = (x ^ (x >> 30)) * 0xBF58476D1CE4E5B9
x = (x ^ (x >> 27)) * 0x94D049BB133111EB
x = x ^ (x >> 31)
```

`x` is the 64-bit output; a uniform in `[0, 1)` is `(x >> 11) * 2^-53`. Every random choice the process makes consumes uniforms from this single stream in a fixed order. A categorical draw over weights `w_0..w_{n-1}` scans in index order and selects the first index whose cumulative sum exceeds the uniform (`u < w_0 + ... + w_i`).

While the process runs, no draws are consumed during a visit. Whenever a visit ends, exactly two draws are consumed, in this order: one categorical draw over the ending state's `A` row picks the next visit's state, then one categorical draw over that state's `D` row picks the new visit's total duration. The recording layer's draws (below) are consumed per step, after the state process has advanced to that step. The one remaining place the stream is consumed is the moment the window opens, and that is defined by the reference.

## What the reference defines

The stream, the categorical scan, the visit-boundary draws, and the recording layer are fully specified above. What is deliberately not documented is the window opening. Its shape is fixed: the setup consumes exactly three draws, and the first is a categorical draw over `pi` that picks the state of the visit in progress. What is left to discovery:

1. what the second and third draws determine about that visit — the law governing its elapsed age and its total length, and which of the two each draw picks;
2. the likelihood's window-opening condition, which matches the process exactly.

The probe reference at `/app/ref` is the authority on both. Your solver must reproduce its semantics exactly, for any input in this format. Every convention is fixed and deterministic; none depends on the input beyond what is written here.

## The probe reference

`/app/ref <input_file> <output_file>` reads any case file in the input schema below and writes the exact output schema below at full double precision. It is a probe tool, not a solver you can wrap: it refuses any case with `T > 128` and any file with more than 200 cases, while the graded inputs run to thousands of steps. Design small cases, run it, and work out the semantics from what it returns.

## Quantities to compute

For each case, compute and report three things, all exact under the reference semantics.

1. The recording `O` — the exact sequence of `T` entries (symbol indices and `?` marks) the reference process emits for the case's `SEED`, entry for entry.

2. The log-likelihood `LOGLIK = log P(O | lambda)` — the natural logarithm of the probability that the process emits this recording, marginalised over all state paths. This is a property of the model, not of the seed: it must be exact for the recording, computed as if the seed were unknown.

3. The expected visit count `NSEG = E[V | O, lambda]`, where `V` is the number of visits the window intersects: 1 plus the number of steps `t` in `1..T-1` at which a visit boundary falls between `t` and `t+1`, given the recording and the model (again marginalised over state paths, not read off the seed's actual path). `NSEG` lies in `[1, T]`.

## Numerical requirement

The likelihood computation must stay correct for long recordings. The shipped cases and the grader's held-out cases include recordings of several thousand steps with small emission probabilities. Any formulation that multiplies raw probabilities straight through underflows to zero on these, after which the log-likelihood collapses to `-inf`. A correct submission must produce finite, accurate values on every case regardless of `T`. How you achieve numerical stability is your choice.

## Input schema

`/app/data/cases.txt` is UTF-8 text holding one or more cases back to back. Blank lines and lines whose first non-space character is `#` are ignored. Each case is:

```
CASE <id>
N <n> K <k> T <t> D <dmax>
SEED <u64>
PI <p_0> <p_1> ... <p_{n-1}>
A <a row of n values>          (n such lines, one jump row each)
B <a row of k values>          (n such lines, one emission row each)
D <a row of dmax values>       (n such lines, one duration row each)
M <m_0> <m_1> ... <m_{n-1}>
END
```

`<id>` is an opaque token with no spaces. `SEED` is an unsigned 64-bit decimal integer. `PI` carries `n` probabilities. There are exactly `n` `A` lines (row `i` of the jump matrix), `n` `B` lines (row `i` of the emission matrix), and `n` `D` lines (row `i` of the duration matrix, `dmax` values). `M` carries `n` values in `[0, 1)`. Probabilities are decimal floats. The solver must also accept an alternate input path and output path as command-line arguments so it can run on other case files.

## Output schema

Write `/app/output/results.txt` (when run with no arguments). For each input case, in input order, emit:

```
CASE <id>
O <t entries>
LOGLIK <log P(O|lambda)>
NSEG <expected visit count>
END
```

`<id>` echoes the input id. The `O` line carries exactly `T` entries, each either a symbol index in `0..k-1` or `?`, separated by single spaces. Emit `LOGLIK` and `NSEG` with full double precision (at least 15 significant digits). The probe reference emits this same schema, so its answers on small cases are directly comparable with your solver's.

## Invocation

```
/app/hmm [input_file [output_file]]
```

With no arguments it reads `/app/data/cases.txt` and writes `/app/output/results.txt`. With arguments it reads `input_file` and writes `output_file` in the same schema. The program must be a self-contained compiled Go binary at `/app/hmm` that does the work itself; it must not call out to another program or interpreter to compute the results, and it must handle any `T`, far beyond the probe reference's cap.

## Tolerance

Each case is checked against an independent exact reference:

- the recording `O` must match entry for entry, exactly;
- `LOGLIK` to within `1e-6` relative (within `1e-6 * (|ref| + 1)` absolute);
- `NSEG` to within `1e-6` relative (within `1e-6 * (|ref| + 1)` absolute).

Independent exact implementations agree on every recording entry and to better than `1e-9` on the analysis quantities even for the longest recordings, so these tolerances are comfortable for an implementation whose semantics match the reference exactly. Any consumption-plan mistake desyncs the recording outright, and every likelihood shortcut — guessed conventions instead of the reference's, ignoring `M`, ignoring the duration structure, or arithmetic that underflows — lands orders of magnitude outside the analysis tolerances.

## Determinism

Everything here is a deterministic computation. Re-running the binary on the same input must reproduce byte-identical output.
