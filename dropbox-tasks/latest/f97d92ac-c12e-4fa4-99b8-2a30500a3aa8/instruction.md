# Reconcile the dual-control settlement key-rotation ceremony

A primary SoftHSM2 token in `/app/ceremony` contains a retiring settlement key whose private half exists only inside that token. A second escrow token contains an escrow private key that also has no filesystem copy. A new settlement key and certificate are staged on disk, but the primary token has no recovery envelope, continuity evidence, escrow receipt, or replacement custody objects yet. Rotate custody without resetting either token or losing unrelated objects.

Create an executable `/app/bin/rotate_ceremony`. With no arguments it must read `/app/ceremony/policy.json` and write `/app/ceremony/rotation-attestation.json`. It must also accept `--policy PATH` and `--output PATH` in either order so the same implementation works for other token pairs and policies. Network access is unavailable. SoftHSM2, OpenSC, OpenSSL, `jq`, and a system Python with PyKCS11 and cryptography are installed locally.

The command must reconcile both live PKCS#11 tokens rather than initialize or replace either token store. It must seal the staged active private key and the exact recovery key into a policy-defined hybrid recovery envelope, use the retiring private key to sign continuity evidence over that envelope, use the escrow private key to countersign the continuity evidence, install the active signing key and recovery key with the required custody attributes, retain all three public certificates, and preserve every object outside the policy's managed identifiers. A valid interrupted or already committed rotation must converge safely on rerun without duplicating objects or regenerating valid envelope, continuity, receipt, or recovery material. A valid envelope must be sufficient to resume after the staged private key has already disappeared. Ambiguous, corrupt, cross-token-inconsistent, or irrecoverable state must fail closed.

The complete policy schema, canonical envelope and signed payloads, PKCS#11 object contracts, reconciliation rules, failure behavior, and exact attestation schema are normative in `/app/ceremony/rotation-spec.md`. Remove any stale requested output before reading or validating inputs. Every failure must return nonzero, leave the requested output absent, and write a diagnostic beginning with `rotate_ceremony:` to stderr. Preflight failures must not change persistent token objects or remove the staged private key. After a successful commit, remove the staged PEM private key named by the policy and leave the attestation with a trailing newline.
