# Mirror operations

The gate's inputs are only as good as the mirrors that produce them.
This chapter documents the mirror layer's obligations to the gate — the
freshness, attestation, and snapshot properties the rules elsewhere
assume. It is operator-facing; nothing here changes gate behavior, but
several gate findings are, in practice, mirror findings wearing a
ledger row's name.

## The four mirrors

**npm mirror.** A caching registry proxy with an attestation database:
at ingest, every tarball's sha512 is recorded against (name, version),
and the provenance verifier consults that record (chapter 24). The
mirror is retention-complete since 2023 — every version ever served is
retained, which is what makes package-quarantine investigations
tractable (QR-2101's investigation failed partly because the pre-mirror
era retained nothing).

**PyPI mirror.** A selective mirror: packages enter on first reference
from a manifest, then track upstream. File-level sha256 attestation at
ingest, same consultation path. The selectivity means a brand-new
dependency's first resolution races the mirror's ingest; the ledger
writer retries once before recording `unverified`, and the FAQ's
"unverified only in CI" pattern is usually this race lost.

**Go module proxy.** A standard module proxy fronting the public
ecosystem plus the private-module first-fetch attestor. Checksum
database inclusion proofs are verified at ingest (chapter 24); the
proxy's transparency-log position is checkpointed daily and the
checkpoint is part of the compliance record's retention set.

**Model registry mirror.** Snapshots upstream repositories into the
content-addressed tree the integrity report hashes (see the registry
snapshot document). Two properties matter to the gate: syncs are
atomic per revision (a revision appears in the snapshot only when all
its files landed — the QR-2178 race predates this), and revisions are
never rewritten in place locally even when upstream rewrites (the
upstream rewrite surfaces as a digest divergence, which is exactly
QR-2311's shape).

## Attestation freshness

Provenance verification consults attestation records, and records age.
The mirror layer's contract with the ledger writer: an attestation is
served only while the mirror still holds the attested bytes; a
retention exception (legal takedown, upstream unpublish) tombstones the
record, and tombstoned attestations verify as `unverified` on the next
ledger write. This is deliberately conservative — the alternative,
serving attestations for bytes the mirror can no longer produce, would
let `verified` mean "was once verifiable," which is not what chapter 07
promises.

Takedowns are rare (four in program history) and each produced a brief
wave of `provenance-unverified` annotations as affected rows re-wrote —
expected behavior, noted here so the next operator does not treat the
wave as an incident. The queue items self-closed as teams re-pinned.

## Snapshot integrity duties

The integrity report the gate consumes is generated by hashing the
model snapshot with OpenSSL at audit time (registry snapshot document).
The mirror's duties around that: the snapshot filesystem is mounted
read-only to everything except the sync process; sync writes go to a
staging path and move atomically; and the sync process emits its own
manifest of (path, digest) at completion, which mirror monitoring diffs
against a fresh hash pass weekly. A monitoring divergence means
corruption at rest and pages mirror operations — before any gate run
notices, in the healthy case.

The weekly pass exists because the gate only hashes *pinned* paths at
audit time. Corruption in a not-yet-pinned file would otherwise sit
undetected until a team pins it, at which point it presents as a
`digest-mismatch` rejection against a brand-new dependency — confusing
for the team, and a week older for the investigation.

## What operators owe an investigation

When a gate finding escalates to an incident (the chapter 08 runbook
pages on `digest-mismatch`), mirror operations brings: the attestation
record and ingest timestamp for the affected version or revision; the
sync logs bracketing the divergence window; the retention status of
every implicated byte range; and, for model artifacts, the upstream
revision history as the mirror observed it. QR-2311's investigation is
the template — the mirror's observation of the upstream rewrite was
the evidence that localized the fault upstream rather than in our
sync.

Mirror operations never "fixes" a divergence by re-syncing over it
while an investigation is open: the divergent bytes are the evidence.
Quarantine-by-digest exists precisely so the investigation can proceed
with the affected artifact immobilized rather than erased.
