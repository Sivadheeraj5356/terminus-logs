Implement `/app/task_file/src/main.rs` in Rust so `rustc /app/task_file/src/main.rs -O -o /tmp/auditor && /tmp/auditor /app/task_file/input/release.txt /app/task_file/output/report.json` audits offline Sigstore-style release attestations. Input records are whitespace tokens: `KEY id issuer subject not_before not_after trusted`, `IMAGE name digest env tier`, `ATTEST name digest predicate builder key timestamp log_index source_digest`, `LOGROOT log_id root_hash not_before not_after trusted`, `BUNDLE log_index log_id integrated_time tree_size root_hash`, `CHECKPOINT log_id tree_size root_hash prev_root_hash prev_tree_size trusted`, `WITNESS log_id tree_size root_hash key timestamp source_digest trusted`, `WITNESSREQ log_id root_prefix min_count distinct-key|same-key-ok max_age [source_prefix]`, `ROOTPIN env tier log_id root_prefix not_before not_after trusted`, `SPLITVIEW log_id tree_size root_hash trusted`, `BIND builder issuer subject_prefix source_prefix env tier not_before not_after trusted`, `KEYSCOPE key env tier builder source_prefix not_before not_after trusted`, `EMBARGO env tier builder source_prefix start end`, `HOLD env tier builder source_prefix marker_predicate marker_builder marker_issuer marker_source_prefix start end`, `CHAIN env tier predicate builder prev_predicate prev_builder max_delta source_prefix`, `UNIQUE env tier`, `REQUIRE env tier predicate builder issuer max_age min_log hard|warn [subject_prefix] [source_prefix]`, `QUORUM env tier label min_count distinct-key|same-key-ok hard|warn [min_source_groups]`, `MEMBER label predicate builder issuer max_age min_log source_prefix [subject_prefix]`, `DELEGATE parent_key child_key not_before not_after subject_prefix source_prefix`, `REQUEST name digest now`, `REVOKE key [start end]`, and `COMPROMISE key start end source_prefix`. Ignore blank lines and lines whose first non-whitespace character is `#`. Parse the whole file before evaluating requests. `REVOKE key` revokes that key for every attestation timestamp; `REVOKE key start end` revokes it only when `start <= attestation timestamp <= end`, even if the revoke line appears after requests, attestations, or delegations. `COMPROMISE key start end source_prefix` invalidates that key only when `start <= attestation timestamp <= end` and the attestation `source_digest` starts with `source_prefix`, with `*` matching every source; compromise records are also parsed globally before request evaluation. Optional `subject_prefix` defaults to `*`; optional `source_prefix` on `REQUIRE` and `WITNESSREQ` defaults to `*`.

All record fields are case-sensitive opaque strings except integer time, index, size, and count fields. A `trusted` field is true only when it is exactly `1`; every other value is false. There is no network access, certificate-chain fetching, cryptographic hash verification, or real Sigstore API call. The audit is entirely determined by the input records above. Unknown record types are not part of the input contract and need not be supported.

Valid inputs do not repeat `KEY` ids or `(IMAGE name,digest)` pairs. All other duplicate records are retained and evaluated as separate records; duplicate policies preserve input order for decisions, warnings, and evidence. The token `*` is a wildcard only in fields where this contract explicitly says it is; it is not a glob pattern and no other wildcard syntax exists.

For each request, find the exact image by matching both name and digest, then apply every matching `REQUIRE` or `QUORUM` policy whose env and tier match that image; duplicate policies are evaluated independently and in input order. A valid attestation for a requirement or member must match name, digest, predicate, and builder; use an existing key whose issuer matches, whose subject starts with `subject_prefix` unless the prefix is `*`, whose inclusive validity window covers the attestation timestamp, whose timestamp is not covered by any revoke record for that key, whose key is not compromised for that timestamp and source digest, with `log_index >= min_log` and `now - timestamp <= max_age`. `EMBARGO` is a secure incident-response gate: an attestation is invalid when any embargo matches the image env, image tier, attestation builder, and source digest prefix, and either the request `now` or the attestation timestamp is inside the embargo's inclusive `[start,end]` window. `*` is a wildcard for embargo env, tier, builder, and source prefix. If any `BIND` record exists for the attestation's builder, at least one `BIND` record for that builder must also be trusted and must match the attesting key issuer, key subject prefix, source digest prefix, image env, image tier, and attestation timestamp; `*` is a wildcard for the issuer, subject prefix, source prefix, env, and tier fields. If any `KEYSCOPE` record exists for the attesting key, at least one `KEYSCOPE` for that key must also be trusted and must match image env, image tier, attestation builder, source digest prefix, and attestation timestamp; `*` is a wildcard for env, tier, builder, and source prefix. Untrusted or expired matching-looking bind/scope records do not authorize the attestation, and builders or keys with no matching record type keep the legacy behavior. If one or more `CHAIN` records match the image env, image tier, attestation predicate, attestation builder, and attestation source prefix, every matching chain rule must be satisfied by at least one prior attestation for the same image name and digest. The predecessor must match `prev_predicate` and `prev_builder`, use a key from the same issuer as the chained attestation key, pass every validity gate in this paragraph except `CHAIN` with wildcard subject/source prefixes, no minimum log floor, and no age limit, have `predecessor.timestamp <= attestation.timestamp`, have `attestation.timestamp - predecessor.timestamp <= max_delta`, and have `predecessor.log_index < attestation.log_index`. `*` is a wildcard for chain env, tier, and source prefix. Builders with no matching `CHAIN` record keep the legacy behavior. A predecessor used only to satisfy `CHAIN` does not emit an evidence row unless it is also selected by a matching `REQUIRE` or `MEMBER`. If any `BUNDLE` record exists for the attestation's `log_index`, at least one such bundle must prove inclusion: its `integrated_time` equals the attestation timestamp, `tree_size > log_index`, and there is a `LOGROOT` with the same `log_id` and `root_hash`, `trusted` equal to `1`, and an inclusive validity window covering the bundle `integrated_time`. A bundle is never valid if a trusted `SPLITVIEW` record exists for the same `log_id`, `tree_size`, and `root_hash`; untrusted split-view records are ignored. If one or more `CHECKPOINT` records exist for that bundle's `(log_id, tree_size, root_hash)`, at least one matching checkpoint must also be trusted, must have `prev_tree_size < tree_size`, and must either use `prev_tree_size=0` or reference a trusted `LOGROOT` with the same `log_id` and `prev_root_hash` whose validity window ends no later than the bundle `integrated_time`. If no matching checkpoint exists, the bundle is accepted by the root rule alone for backward-compatible inputs. If no bundle exists for that log index, accept the attestation as a legacy entry for backward-compatible inputs. The key must either be directly trusted (`trusted` is `1`) or have a valid delegation chain to a directly trusted key at the attestation timestamp. A delegation edge is valid only when `parent_key` is trusted by the same recursive rule, `child_key` is the attesting key or an intermediate delegated key, the attestation timestamp is inside the delegation's inclusive window, the child key subject starts with the delegation `subject_prefix` unless it is `*`, and the attestation `source_digest` starts with the delegation `source_prefix` unless it is `*`. Revocation and compromise apply to every key in the chain at the attestation timestamp and source digest; cycles do not establish trust. Apply the age formula literally, so future attestations with `timestamp > now` are valid if the resulting negative age still satisfies `<= max_age`. `source_digest` must start with the applicable requirement/member `source_prefix`, except `*` matches every source. Pick single-requirement evidence by newest timestamp, then highest log index, then earliest attestation record. Missing hard requirements deny with `missing:predicate:builder`; missing warn requirements only populate warnings.

`HOLD` records model incident-response holds that become active only when the release already contains a valid hold marker attestation for the same image name and digest. A candidate attestation is invalidated by a hold when the hold env, tier, builder, and source prefix match that candidate and either request `now` or the candidate timestamp is inside the hold's inclusive `[start,end]` window. `*` is a wildcard for hold env, tier, builder, source prefix, and marker source prefix. A hold marker is an attestation for the same image whose predicate and builder match `marker_predicate` and `marker_builder`, whose key issuer is exactly `marker_issuer`, whose source digest starts with `marker_source_prefix` unless it is `*`, and which passes key validity, revocation, compromise, delegation trust, builder binding, key scoping, and transparency checks. For marker builder binding and marker key scoping, use the marker attestation's builder, key, source digest, and timestamp with the requested image's env and tier. Hold markers are not invalidated by `EMBARGO`, `HOLD`, `CHAIN`, age, min-log, `REQUIRE`, or `QUORUM`; they are marker facts, not selected release evidence, unless independently selected by a policy. Hold invalidation applies to direct requirements, quorum member candidates, and predecessor attestations considered for `CHAIN`. Duplicate holds are retained; any active matching hold invalidates the candidate.

Transparency fallback is intentionally strict: legacy acceptance applies only when there are zero `BUNDLE` records with the attestation's `log_index`. If any bundle exists for that index but every candidate bundle fails its time, tree-size, root, split-view, checkpoint, root-pin, or witness checks, the attestation is invalid. Multiple bundles for one index are alternatives; one valid bundle is enough. Multiple checkpoints for one bundle are also alternatives; one valid matching checkpoint is enough. A trusted `SPLITVIEW` matching a bundle rejects only that bundle, not other bundles with different roots, log ids, or tree sizes.

`ROOTPIN` adds optional environment-scoped transparency root pinning. A bundle must satisfy a trusted root pin when one or more `ROOTPIN` rows match the requested image env, image tier, and bundle `log_id`; `*` is a wildcard for env, tier, log id, and root prefix. A matching pin authorizes the bundle only when it is trusted, its inclusive validity window covers the bundle `integrated_time`, and its `root_prefix` is `*` or is a prefix of the bundle `root_hash`. Untrusted, expired, wrong-env, wrong-tier, wrong-log, or wrong-root pins do not authorize the bundle. If no root pin matches the image env/tier/log, legacy transparency behavior applies. Root pins are checked for direct evidence, quorum member evidence, chain predecessors, and hold markers using the requested image's env and tier.

`WITNESSREQ` adds an optional witness quorum for transparency bundles. A bundle must satisfy every `WITNESSREQ` whose `log_id` equals the bundle log and whose `root_prefix` is `*` or is a prefix of the bundle `root_hash`; if no witness requirement matches, legacy transparency behavior applies. A valid witness must match the bundle `log_id`, `tree_size`, and `root_hash`, have `trusted` exactly `1`, have `timestamp <= integrated_time`, satisfy `integrated_time - timestamp <= max_age`, and have `source_digest` starting with the requirement `source_prefix` unless it is `*`. The witness `key` must exist, be inside its key validity window at the witness timestamp, not be revoked or compromised at that timestamp and witness source digest, and be directly trusted or delegated by the same `DELEGATE` trust rule used for attestations. For `distinct-key`, counted witnesses must use pairwise distinct keys; `same-key-ok` allows repeated keys on different witness rows. Duplicate witness rows count separately only when the mode allows their keys to be reused. Witness rows do not emit evidence and do not affect release policy selection except through bundle validity.

Delegation is evaluated from the attesting key back toward a directly trusted key. Every key on the chosen path, including the directly trusted root key and all intermediate keys, must be present, inside its own key validity window, not revoked, and not compromised for the attestation timestamp and source digest. The issuer checked against a `REQUIRE` or `MEMBER` is the issuer of the attesting key, not the issuer of a delegating parent.

`QUORUM` policies use all `MEMBER` records with the same label, in member input order. A quorum is satisfied when at least `min_count` members can each select one valid attestation; for `distinct-key`, selected attestations must use pairwise distinct keys, while `same-key-ok` allows reuse. If optional `min_source_groups` is present and greater than zero, the selected quorum attestations must also cover at least that many distinct source groups. A source group is the substring before the first `/` in `source_digest`, or the entire `source_digest` when it contains no `/`. Select quorum evidence by maximizing this deterministic score over all valid member selections: first the number of selected members, then the number of distinct selected source groups, then for each member in input order prefer selected over missing, newer timestamp, higher log index, and earlier attestation record. Emit evidence only for selected members, in member input order. If no selection reaches `min_count` and `min_source_groups`, emit no partial quorum evidence and use the missing string `missing:quorum:label` as either a hard reason or warning according to the quorum policy.

A satisfied quorum may select more than `min_count` members because selected-member count is the first optimization criterion. For `distinct-key`, the same attestation key cannot be used by two selected members in the same quorum, even if the attestations are different records. For `same-key-ok`, the same key and even the same attestation record may satisfy multiple members when it independently matches each member rule.

`UNIQUE env tier` activates per-request evidence reuse control for matching images. When at least one `UNIQUE` row matches an image's env and tier, a single `ATTEST` record may be emitted as evidence at most once across all matching `REQUIRE` and `QUORUM` policies for that request. Policies still run in input order: each satisfied policy reserves the attestation records it emits, and later policies must choose different valid attestation records or become missing. Inside a unique-enabled quorum, the same attestation record cannot satisfy two selected members even when the quorum mode is `same-key-ok`; `distinct-key` still additionally requires distinct keys. `UNIQUE` does not affect hold markers or chain predecessors unless those attestations are also selected as emitted policy evidence, and duplicate `UNIQUE` rows have the same effect as one.

Edge-case clarifications:

- `BIND` strictness is builder-wide. If even one `BIND` row exists for a builder, every attestation by that builder needs at least one currently trusted matching `BIND`; stale, untrusted, wrong-env, wrong-tier, wrong-issuer, wrong-subject, or wrong-source bind rows do not authorize it. The `BIND` time window is checked against the attestation timestamp, not request `now`.
- Hold-marker binding uses the marker attestation's own builder, key issuer, key subject, source digest, and timestamp, but the requested image's env and tier. Therefore a `BIND` row for the marker builder can prevent hold activation when it does not match the marker key/source, even if the marker has the right predicate and issuer.
- `CHAIN` predecessors are ordinary candidate attestations for validity purposes: they must pass trust, revocation, compromise, `BIND`, `KEYSCOPE`, `EMBARGO`, `HOLD`, and transparency checks, including `SPLITVIEW`, `CHECKPOINT`, `ROOTPIN`, and `WITNESSREQ`, before they can satisfy a chain. They do not apply chain recursively, policy age, policy min-log, or policy subject/source prefixes. If every possible predecessor is removed by hold, split-view, bad checkpoint/root, stale or nonmatching bind, stale or nonmatching key scope, root pin, witness quorum, embargo, revocation, or compromise, the chained attestation is invalid.

Emit deterministic valid JSON with exactly three top-level keys in this order: `decisions`, `evidence`, `summary`. JSON string values must escape quotation marks, backslashes, and every control character U+0000 through U+001F according to JSON syntax; opaque input tokens are not sanitized, normalized, or otherwise changed before encoding. The output must end with one trailing newline. `decisions` follows request order. Each decision object must use exactly these keys in this order: `request`, `status`, `reasons`, `warnings`. The `request` value is the compact string `name@digest` from the `REQUEST` record. `status` is the string `approved` when no hard `REQUIRE` or hard `QUORUM` policy is missing, otherwise `denied`. `reasons` is a list of hard-denial reason strings in matching policy order. `warnings` is a list of warn-missing strings in matching policy order. If the requested image does not exist, emit one denied decision with `reasons: ["image-missing"]`, empty `warnings`, no evidence, and do not evaluate policies for that request.

`evidence` follows decision order, then matching policy order; duplicate `REQUIRE` policies emit duplicate evidence entries when satisfied. For a satisfied `QUORUM`, emit one evidence entry for each selected member in member input order at that quorum's policy position. Each evidence object must use exactly these keys in this order: `request`, `predicate`, `builder`, `key`, `timestamp`, `log_index`, `source_digest`. `request` again uses `name@digest`. The remaining values come from the selected attestation, except `predicate` and `builder`, which come from the satisfied `REQUIRE` or from the selected `MEMBER` for quorum evidence. Do not include separate image name or digest fields, issuer fields, booleans, or extra diagnostic fields.

`summary` must use exactly these keys in this order: `requests`, `approved`, `denied`, `warnings`. `requests` is the number of `REQUEST` records. `approved` and `denied` count decisions by status. `warnings` is the total number of missing warn `REQUIRE` and warn `QUORUM` policies across all approved or denied decisions. The canonical missing-requirement string is exactly `missing:predicate:builder`; the canonical missing-quorum string is exactly `missing:quorum:label`; the canonical missing-image string is exactly `image-missing`.
