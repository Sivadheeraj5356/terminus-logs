# Stateful service failover readiness rules

The operator maintains one safety dossier for the service group named in `/app/records/incident.tsv`. The dossier is the failover authority: it must decide whether the standby host can take traffic, mounts, credentials, routes, and rollback responsibility without split-brain or exposed held services. The checker may replace every file under `/app/records` with another same-contract estate before `/app/solve.sh` runs, so a dossier that copies the sample incident, emits fixed host/service decisions, or substitutes one summary file for the required evidence is invalid. The dossier root is `/app/dossier`. It must contain exactly these files: `decision/failover-verdict.json`, `decision/start-order.tsv`, `decision/hold-list.tsv`, `decision/rollback-window.json`, `evidence/health-ledger.tsv`, `evidence/quorum-ledger.tsv`, `evidence/fencing-ledger.tsv`, `evidence/mount-ledger.tsv`, `evidence/route-ledger.tsv`, `evidence/credential-ledger.tsv`, `attestations/dependency-attestation.json`, `attestations/quorum-attestation.json`, `attestations/fencing-attestation.json`, `attestations/route-attestation.json`, `attestations/rollback-attestation.json`, and `index/incident-index.json`.

All records are tab-separated with a header row. The incident epoch is an integer. A record is current only when its `evidence_epoch` equals the incident epoch, except credential windows and rollback records, which use the explicit fields described below. Sort service IDs, host IDs, and artifact paths lexicographically unless a rule names another order. JSON files use UTF-8, LF newlines, two-space indentation, sorted keys, and one trailing newline. Fingerprints are lowercase SHA-256 hex digests of the exact normalized file bytes.

`incident.tsv` contains `key<TAB>value` rows for `incident_epoch`, `root_service`, `old_active_host`, and `quorum_threshold`. `hosts.tsv` contains `host_id`, `priority`, and `host_group`. The old active host is never a candidate target. Among legal targets, choose the lowest numeric priority and then the lexicographically smallest host ID.

`health.tsv` contains `host_id`, `status`, and `evidence_epoch`. Valid status values are `UP`, `DEGRADED`, and `DOWN`; precedence from safest to worst is `UP`, `DEGRADED`, `DOWN`, and missing current evidence. A candidate host may be used only with current `UP` or `DEGRADED` health. The health ledger lists every host from `hosts.tsv` as `host_id<TAB>status<TAB>current<TAB>eligible`, sorted by host ID. `current` and `eligible` are `YES` or `NO`.

`quorum.tsv` contains `candidate_host`, `voter_host`, `reachable`, and `evidence_epoch`. Count only rows for the candidate whose epoch is current, whose voter appears in `hosts.tsv`, whose voter is not `DOWN` in the current health ledger, and whose `reachable` value is `YES`. A candidate owns a safe quorum view when this count is at least `quorum_threshold`. The quorum ledger lists every candidate host except the old active host as `candidate_host<TAB>reachable_votes<TAB>threshold<TAB>quorum_status`, sorted by candidate host; the status is `PASS` or `FAIL`.

`services.tsv` contains `service_id`, `priority`, `requires_mount`, `route_scope`, `credential_id`, and `irreversible_barrier`. The service graph consists of every service in this file plus edges from `dependencies.tsv`, whose columns are `service_id` and `depends_on`. A service can start only when all ancestors can start. The start order is `order<TAB>service_id<TAB>target_host`, ordered by dependency closure and then numeric service priority and service ID. The hold list is `service_id<TAB>reason`, sorted by service ID; a service is held for the earliest applicable reason in this order: `CREDENTIAL_BLOCKED`, `MOUNT_BLOCKED`, `DEPENDENCY_HELD`, `ROUTE_BLOCKED`.

`credentials.tsv` contains `credential_id`, `host_group`, `not_before`, `not_after`, and `revoked`. A credential is valid for a target only when `revoked` is `NO`, `not_before <= incident_epoch <= not_after`, and the credential host group equals the target host group. The credential ledger lists every service as `service_id<TAB>credential_id<TAB>credential_status`, sorted by service ID; status is `PASS` or `FAIL`.

`leases.tsv` contains `volume_id`, `holder_host`, `authority`, `lease_state`, `evidence_epoch`, and `can_fence`. `mounts.tsv` contains `service_id`, `volume_id`, and `current_owner`. A mounted service is safe on the target when every required volume is either already held by the target or the old holder can be fenced by a current lease row whose `can_fence` is `YES`. The fencing ledger lists `volume_id<TAB>previous_holder<TAB>fence_status`, sorted by volume ID; status is `NOT_NEEDED`, `FENCED`, or `FAIL`. The mount ledger lists `service_id<TAB>volume_id<TAB>target_host<TAB>mount_status`; status is `PASS` or `FAIL`.

`routes.tsv` contains `service_id`, `allowed_scope`, and `current_host`. A started service with `route_scope` other than `internal` must have a route record, and that record's `allowed_scope` must equal the service `route_scope`; otherwise the route status is `FAIL`. A valid started service advertises exactly its allowed scope on the selected target; `current_host` is only the pre-failover host recorded in the input. A held service must set both `advertised_host` and `advertised_scope` to `NONE`. The route ledger lists every service as `service_id<TAB>advertised_host<TAB>advertised_scope<TAB>route_status`; status is `PASS`, `HELD`, or `FAIL`. If a service would otherwise be startable but its route record does not allow its required scope, that service is held with reason `ROUTE_BLOCKED` and its route row has status `FAIL`.

`rollback.tsv` contains `old_host_destroyed`, `route_rollback`, and `storage_reattach`. Rollback is viable only when those values are `NO`, `YES`, and `YES`, and no started service has `irreversible_barrier` set to `YES`. The rollback window JSON contains `rollback_status`, `target_host`, and `blockers`. The status is `AVAILABLE` or `BLOCKED`; blockers are sorted strings from `OLD_HOST_DESTROYED`, `ROUTE_ROLLBACK_BLOCKED`, `STORAGE_REATTACH_BLOCKED`, and `IRREVERSIBLE_SERVICE:<service_id>`.

The failover verdict JSON contains `incident_epoch`, `root_service`, `old_active_host`, `target_host`, `verdict`, and `earliest_blocker`. `verdict` is `FAILOVER_READY` when the target exists, the root service can start, and rollback is available; otherwise it is `NO_SAFE_FAILOVER`. If no host is selected because no current healthy candidate exists or because no healthy candidate has quorum, `target_host` is the empty string `""`. `earliest_blocker` is `NONE` for a ready cutover. If no target exists, use `NO_HEALTHY_TARGET` before `QUORUM_BLOCKED`. After a target exists, evaluate blocker stages in this order: fencing, mounts, the root service's own hold-list reason, routes, and rollback. A fencing-stage failure reports `FENCING_BLOCKED`; a mount-stage failure reports `MOUNT_BLOCKED`; a route-stage failure reports `ROUTE_BLOCKED`; and unavailable rollback after the root service can start reports `ROLLBACK_BLOCKED`. In particular, when the root service is held because one of its ancestors is held, report the root service reason `DEPENDENCY_HELD` rather than the ancestor's lower-level cause.

The five attestation JSON files name `incident_epoch`, `target_host`, `status`, and `evidence`. Their statuses must agree with the ledgers they cite, and `evidence` is a semicolon-separated string with no spaces. The dependency attestation uses `decision/start-order.tsv;decision/hold-list.tsv;evidence/credential-ledger.tsv;evidence/mount-ledger.tsv` and is `PASS` only when every started service follows all dependencies and every held service uses the earliest public reason; otherwise it is `FAIL`. The quorum attestation uses `evidence/quorum-ledger.tsv;evidence/health-ledger.tsv` and cites the selected target's quorum ledger row. The fencing attestation uses `evidence/fencing-ledger.tsv;evidence/mount-ledger.tsv`. The route attestation uses `evidence/route-ledger.tsv;decision/hold-list.tsv`. The rollback attestation uses `decision/rollback-window.json;evidence/route-ledger.tsv;evidence/mount-ledger.tsv`; its `status` is exactly the rollback window's `rollback_status`, so it uses `AVAILABLE` or `BLOCKED`, not `PASS` or `FAIL`.

The index JSON contains `incident_epoch`, `root_service`, `target_host`, `verdict`, `artifact_count`, `artifacts`, and `dependency_edges`. `artifacts` maps each dossier-relative path to its SHA-256 fingerprint. The index fingerprint map must omit the index itself. `dependency_edges` is an exact sorted list of two-item arrays: one edge from `index/incident-index.json` to every other dossier artifact; `attestations/dependency-attestation.json` to `decision/start-order.tsv` and `decision/hold-list.tsv`; `attestations/fencing-attestation.json` to `evidence/fencing-ledger.tsv`; `attestations/quorum-attestation.json` to `evidence/quorum-ledger.tsv`; `attestations/rollback-attestation.json` to `decision/rollback-window.json`; `attestations/route-attestation.json` to `evidence/route-ledger.tsv`; and `decision/failover-verdict.json` to `attestations/quorum-attestation.json` and `attestations/fencing-attestation.json`. Do not add extra dependency edges.
