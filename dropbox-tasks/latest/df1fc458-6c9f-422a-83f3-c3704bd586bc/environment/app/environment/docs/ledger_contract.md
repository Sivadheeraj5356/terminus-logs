# Security assurance contract for the signed KEV remediation ledger

`/app/bin/kev-ledger` is the offline integrity gate for signed KEV evidence and signed remediation decisions. It must establish publisher authenticity and byte integrity before interpreting either input stream, then build the auditable remediation ledger described below. The defaults are `--index /app/data/catalog_fragments/index.json`, `--config /app/config/profiles.json`, `--actions /app/config/remediation_actions.jsonl`, `--trust-store /app/config/trusted_publishers.json`, `--actions-signer agency-actions`, `--profile bod26`, `--state-dir /app/state`, and `--out-dir /app/out`. If `--actions-signature` is omitted, the signature path is the action path with `.sig` appended. All paths accepted by flags must stay inside `/app`; any path traversal or absolute path outside `/app` is a validation failure.

All index, profile-config, and trust-store documents must decode to JSON objects. JSON-valid arrays, scalars, or null values are schema failures, not uncaught exceptions. A selected profile is schema-valid only when it is an object with `include_vendors` as an array of strings, `include_cwe_classes` as an array of strings, and `due_soon_days` as an integer. Missing fields, scalar replacements, or non-string array members in the selected profile are run-level `config_schema_invalid` failures.

All security-sensitive paths are checked both lexically and after filesystem resolution. Every flag path and each required relative fragment, fragment-signature, and trust-key path rejects raw `..` components. Existing input, trust-key, action-signature, and resume targets must resolve inside `/app`; dangling or escaping symlinks are unsafe. Output and state directories must resolve through safe parent chains inside `/app`, including the output `state/` directory itself. A pre-existing leaf symlink at a generated artifact path is different: unlink that leaf and replace it with a regular file, and never open or truncate the symlink target. This replacement rule applies to `kev-ledger.json`, each generated TSV/JSON/manifest file, `error-report.json`, `out-dir/state/kev-ledger.state.json`, and `state-dir/kev-ledger.state.json`.


## Run-level error reason catalog

Run-level validation uses the stable `reason` strings in this section. These names are part of the public contract; do not substitute synonymous names such as `unsafe_path`, `unsafe_state_dir`, or `index_unreadable` when the path itself is unsafe.

| Scope | Unsafe-path reason | Unreadable / invalid reason |
| --- | --- | --- |
| `--index` | `unsafe_index_path` | `index_unreadable`, `index_schema_invalid` |
| `--config` | `unsafe_config_path` | `config_unreadable`, `config_schema_invalid`, `unknown_profile` |
| `--actions` | `unsafe_actions_path` | `actions_unreadable` |
| `--actions-signature` or default action signature | `unsafe_actions_signature_path` | `actions_signature_unreadable`, `actions_signature_invalid`, `untrusted_actions_signer` |
| `--trust-store` | `unsafe_trust_store_path` | `trust_store_unreadable`, `trust_store_schema_invalid` |
| trust-store `public_key` paths | `unsafe_trust_key_path` | `trust_key_unreadable`, `trust_key_invalid` |
| `--resume-from` | `unsafe_resume_path` | `resume_unreadable`, `resume_fingerprint_mismatch` |
| `--state-dir` and its checkpoint target | `unsafe_state_path` | none |
| `--out-dir`, generated artifacts, and the output `state/` subtree | `unsafe_output_path` | none |
| catalog fragment `path` entries | `unsafe_fragment_path` | `fragment_unreadable` |
| catalog fragment `signature` entries | `unsafe_fragment_signature_path` | `fragment_signature_unreadable`, `fragment_signature_invalid`, `untrusted_fragment_signer` |

Path safety is checked before unreadability, schema validation, authentication, parsing, or resume fingerprint comparison. A raw `..` component, an absolute path outside `/app`, an input/resume/trust symlink that resolves outside `/app`, or an output/state directory parent chain that would write outside `/app` is always reported with that scope's `unsafe_*_path` reason. Do not report `unsafe_output_path` or `unsafe_state_path` merely because the final generated file already exists as a symlink; replace that leaf symlink as described above. Only a path that is lexically safe and resolves inside its allowed root may use an unreadable reason. If `--resume-from` names an unsafe checkpoint path, report `unsafe_resume_path` before comparing config, input, or action fingerprints.

## Evidence authentication

The trust store is JSON with `schema_version: "kev.trust.v1"` and a `publishers` object. Each publisher record has one absolute `public_key` path under `/app` containing an Ed25519 PEM public key. A PEM file for another algorithm, even if it is a valid public key, is not trusted and is a run-level `trust_key_invalid` failure. Catalog and action signatures are detached Ed25519 signatures over the exact file bytes, encoded as one base64 string in a `.sig` file. Verification happens before JSON parsing or fingerprint comparison. A signature from an unknown publisher, malformed base64, unreadable signature/key, a non-Ed25519 key, or a cryptographic mismatch is a run-level failure; no success artifact may be promoted from unauthenticated bytes.

Catalog signature paths are relative to the index directory, must remain inside it, and must end in `.sig`. Action signature paths must remain under `/app` and end in `.sig`. The catalog error reasons are `unsafe_fragment_signature_path`, `fragment_signature_unreadable`, `fragment_signature_invalid`, and `untrusted_fragment_signer`. For `untrusted_fragment_signer`, the error report details object is exactly `{"signer": "<fragment signer value>"}`. The action equivalents are `unsafe_actions_signature_path`, `actions_signature_unreadable`, `actions_signature_invalid`, and `untrusted_actions_signer`; for `untrusted_actions_signer`, details is exactly `{"signer": "<actions signer value>"}`. Trust-store/key failures use `trust_store_unreadable`, `trust_store_schema_invalid`, `unsafe_trust_store_path`, `unsafe_trust_key_path`, `trust_key_unreadable`, or `trust_key_invalid`.

## Inputs

The fragment index is JSON with `schema_version: "kev.index.v1"` and a `fragments` array. Each fragment entry has `path`, `source`, `generation`, `signer`, and `signature`. `path` is relative to the index file directory and must resolve to an existing `.jsonl` file inside that directory. `signature` is a relative `.sig` path in the same directory tree, and `signer` must name a publisher in the trust store. Fragment rows are JSON objects with these required fields: `seq` integer, `cveID`, `vendorProject`, `product`, `vulnerabilityName`, `dateAdded`, `dueDate`, `knownRansomwareCampaignUse`, `notes`, and `cwes`. Optional `requiredAction` and `shortDescription` may be present in fragment rows, but they are not copied into any output object unless another schema explicitly names them. The `lineage` array never contains a `details` object and never contains these optional fields. Profile config is JSON with `schema_version: "kev.profiles.v1"`, `as_of`, and `profiles`. A requested profile must exist. Each profile has `include_vendors`, `include_cwe_classes`, and `due_soon_days`. `include_vendors: ["*"]` includes every vendor after trimming whitespace. Otherwise, vendors are matched after trimming and case-folding.

The action overlay is signed JSONL. The default overlay is `/app/config/remediation_actions.jsonl`, and `--actions PATH` may point to another `.jsonl` file inside `/app`. Its detached signature defaults to `<actions-path>.sig`; `--actions-signature` and `--actions-signer` may override the signature file and trust-store publisher. Each action row has required fields `seq` integer, `cve_id`, `action`, `owner`, `ticket`, `effective_date`, `expires_on`, and `source`. Valid `action` values are `defer`, `escalate`, `suppress`, and `clear`. Dates use `YYYY-MM-DD`; `expires_on` must be the same as or later than `effective_date`. Action rows are deduplicated by `cve_id`: highest `seq` wins, and ties use lexicographically smallest `source`. A deduplicated action is active only when `effective_date <= config.as_of <= expires_on`; inactive actions are still reported with `applied: false` but do not change ledger entries. The `applied` boolean is evaluated entirely from that date window after action-row deduplication; it does not depend on profile membership, whether the CVE remains in `entries`, or whether the CVE is selected in `lineage`.

## Validation

A catalog row is invalid when a required field is missing, `seq` is not an integer, `cveID` does not match `CVE-YYYY-NNNN...`, a date is not `YYYY-MM-DD`, `dueDate` is earlier than `dateAdded`, `knownRansomwareCampaignUse` is not `Known` or `Unknown`, `cwes` is not a non-empty array of `CWE-NNN` strings, or trimmed `vendorProject`, `product`, or `vulnerabilityName` is empty. Invalid rows must be reported in `invalid_rows` and excluded from all ledger entries and summaries. Invalid row error strings are stable contract values: missing fields use `missing_<fieldName>`, invalid scalar fields use `<field>_invalid` with `date_added_invalid`, `due_date_invalid`, `seq_invalid`, `cve_invalid`, `ransomware_invalid`, and `cwes_invalid`, blank string fields use `<fieldName>_blank`, and due dates before date-added use `due_before_added`. Missing-field and value-validation errors accumulate independently for every required field that has a validator. The catalog dual-error fields are `seq`, `cveID`, `dateAdded`, `dueDate`, `knownRansomwareCampaignUse`, `vendorProject`, `product`, `vulnerabilityName`, and `cwes`: an absent `seq` yields both `missing_seq` and `seq_invalid`; absent `vendorProject`, `product`, or `vulnerabilityName` yields both `missing_<fieldName>` and `<fieldName>_blank`; and the other listed absent fields likewise yield both their `missing_...` error and their normal invalid error. Missing `notes` yields only `missing_notes` because no additional value validator applies to it.

Each ordinary `invalid_rows` object has exactly `source`, `generation`, `seq`, `cve_id`, `errors`, and `line`. A non-empty catalog line that cannot be parsed as JSON is a row-level validation failure, not a run-level failure. Add exactly one `invalid_rows` object with `source` and `generation` copied from the fragment index entry, `seq: null`, `cve_id: null`, `errors: ["json_invalid"]`, the one-based fragment-file `line`, and `message` set to the JSON parser error text. The required parse-failure error code is the literal string `json_invalid`; do not substitute a generic catalog or schema error. `errors` is sorted lexicographically for all invalid rows. Invalid rows are sorted by `source`, then numeric `generation`, then numeric `line`, then `cve_id` as a string with null treated as an empty string. Invalid index/config shape, unsafe paths, unreadable fragments, unknown profile, unsafe action path, unreadable action file, or resume fingerprint mismatch are run-level failures. An index fragment path that is absolute, contains `..`, resolves outside the index directory, or does not end in `.jsonl` fails the run with reason `unsafe_fragment_path` and `details: {"path": "<fragment path>"}`. An action overlay path outside `/app`, a path with traversal, or a path that does not end in `.jsonl` fails the run with reason `unsafe_actions_path` and `details: {"path": "<action path>"}`.

An action row is invalid when a required field is missing, `seq` is not an integer, `cve_id` is not a CVE id, `action` is not one of the four valid action values, `owner`, `ticket`, or `source` trims to an empty string, either action date is invalid, or `expires_on` is before `effective_date`. Invalid action errors use stable strings: `missing_<fieldName>`, `seq_invalid`, `cve_invalid`, `action_invalid`, `owner_blank`, `ticket_blank`, `source_blank`, `effective_date_invalid`, `expires_on_invalid`, and `expired_before_effective`. Action validation is cumulative in the same way as catalog validation. The action dual-error fields are `seq`, `cve_id`, `action`, `owner`, `ticket`, `effective_date`, `expires_on`, and `source`: a missing required field in that list emits both `missing_<fieldName>` and the corresponding invalid-or-blank error (`seq_invalid`, `cve_invalid`, `action_invalid`, `owner_blank`, `ticket_blank`, `effective_date_invalid`, `expires_on_invalid`, or `source_blank`). Each `invalid_actions` object has exactly four fields: `seq`, `cve_id`, `errors`, and `line`. Do not append `message`, `source`, raw-row data, or any other extra key. For a decoded JSON action row that fails validation, `seq` stores the raw parsed `seq` value from that row, including a non-integer string such as `"bad"` or a JSON null; only an absent `seq` key or a JSON parse failure uses null. Do not coerce non-integer strings to null. JSON parse failures use `seq: null`, `cve_id: null`, `errors: ["json_invalid"]`, and the one-based line number. A JSON-valid action value that is not an object uses `seq: null`, `cve_id: null`, and `errors: ["json_object_required"]`. Invalid actions are sorted by numeric `line`, then `cve_id` as a string with null treated as empty.

## Deduplication, profile selection, and action effects

Valid catalog rows are deduplicated by `cveID`. The winning row for a CVE is the row with highest fragment `generation`; ties use highest `seq`; remaining ties use lexicographically smallest fragment `source`. Deduplication happens before profile filtering. Profile filtering then removes winners whose vendor is not included or whose CWE classes do not intersect `include_cwe_classes`. Known CWE classes are: `code-execution` = `CWE-78`, `CWE-94`, `CWE-502`, `CWE-306`, `CWE-918`; `path-traversal` = `CWE-22`, `CWE-61`; `auth-integrity` = `CWE-284`, `CWE-287`, `CWE-347`; `input-validation` = `CWE-20`; and `memory-safety` = `CWE-119`, `CWE-787`. Unknown CWEs use class `other`.

Action effects are applied after catalog deduplication and profile filtering decide which CVEs can appear as ledger entries. The action object still reports `applied` from its own date window even when that CVE is outside the selected profile or later removed from `entries`. An active `suppress` action removes the entry from `entries` and makes the corresponding lineage `selected` value `false`. An active `defer` action changes `status` to `deferred` but leaves the computed priority unchanged. An active `escalate` action changes `priority` to `emergency` but leaves status unchanged. `clear` is reported as an action but has no effect. Multiple action rows for the same CVE never stack because action rows are deduplicated before application.

## Ledger fields and ordering

Each ledger entry has exactly the following key set; this is a membership list, not a serialization order: `cve_id`, `vendor`, `product`, `vulnerability_name`, `date_added`, `due_date`, `ransomware`, `cwe_classes`, `status`, `priority`, `source`, `generation`, `seq`, and `notes_digest`. The canonical serializer orders every object key lexicographically and recursively. The stored `vendor`, `product`, and `vulnerability_name` values are the corresponding source strings with leading and trailing whitespace stripped. `notes_digest` is the SHA-256 hex digest of the exact `notes` string. Without an active defer action, `status` is `overdue` if `due_date` is before config `as_of`, `due_soon` if it is within `due_soon_days` days after `as_of` inclusive, otherwise `open`; active defer uses status `deferred`. `priority` is `emergency` when ransomware is `Known` or the remediation window from `date_added` through `due_date` is 7 days or less, `accelerated` when that same date-added-to-due-date window is 14 days or less or the entry has a `code-execution` class, otherwise `standard`; active escalate forces `emergency`. The priority due window is not measured from config `as_of`. `cwe_classes` is sorted alphabetically. Ledger entries are sorted by `status_rank` (`overdue`, `due_soon`, `deferred`, `open`), then `priority_rank` (`emergency`, `accelerated`, `standard`), then lowercase vendor, lowercase product, and `cve_id`.

The top-level ledger object has exactly `schema_version`, `summary`, `entries`, `actions`, `invalid_rows`, `invalid_actions`, and `lineage`; its `schema_version` value must be exactly `kev.ledger.v1`. Each action object has exactly `cve_id`, `action`, `source`, `seq`, `owner`, `ticket`, `effective_date`, `expires_on`, and `applied`, sorted by `cve_id`. `summary` has `profile`, `as_of`, `entry_count`, `invalid_row_count`, `action_count`, `invalid_action_count`, `by_status`, `by_priority`, `by_vendor`, `by_action`, `input_fingerprint`, and `actions_fingerprint`. Count maps must have sorted keys; `by_action` counts only applied deduplicated actions. `lineage` contains one object for every valid winning catalog row after catalog deduplication, sorted by `cve_id`; each lineage object has exactly these five keys: `cve_id`, `source`, `generation`, `seq`, and `selected`. No `details`, `requiredAction`, `shortDescription`, or other extra keys are allowed in lineage entries.

## Success artifacts

On success, the output directory must contain these files and no stale failure file: `kev-ledger.json`, `entries.tsv`, `actions.tsv`, `vendor-summary.tsv`, `rebuild-ledger.json`, `manifest.sha256`, and `state/kev-ledger.state.json`. The `--state-dir` flag is a separate state write destination: when it differs from the output directory's `state` subdirectory, the same state JSON must also be written to `--state-dir/kev-ledger.state.json`. This dual-write behavior is required so an audit package can be stored under one output directory while resume checkpoints live in a stable external state directory. JSON must be canonical: UTF-8, no pretty printing, sorted object keys recursively, and exactly one trailing newline. TSV files use LF line endings and include headers. `entries.tsv` columns are `cve_id`, `vendor`, `product`, `status`, `priority`, `due_date`, `ransomware`, `cwe_classes`, sorted exactly like ledger entries; `cwe_classes` is `|`-joined. `actions.tsv` columns are `cve_id`, `action`, `applied`, `owner`, `ticket`, `expires_on`, sorted exactly like the ledger `actions` array; `applied` is the lowercase string `true` or `false`. `vendor-summary.tsv` columns are `vendor`, `entry_count`, `emergency`, `accelerated`, `standard`, sorted by lowercase vendor.

`rebuild-ledger.json` is built from the TSV exports and must contain `schema_version`, `entry_count`, `action_count`, `vendor_count`, `entries_digest`, `actions_digest`, and `vendor_summary_digest`; its `schema_version` value must be exactly `kev.rebuild.v1`. `manifest.sha256` contains one SHA-256 line for each of `actions.tsv`, `entries.tsv`, `kev-ledger.json`, `rebuild-ledger.json`, and `vendor-summary.tsv` in the form `<hex>  <path>`. Manifest order is lexicographic over the complete line string, not over the relative path column alone. The file uses LF line endings and one final trailing newline.

The state file records `schema_version: "kev.state.v1"`, `profile`, `config_fingerprint`, `input_fingerprint`, `actions_fingerprint`, `ledger_digest`, and `generation_max`. `input_fingerprint` is the SHA-256 digest over a canonical JSON array of objects sorted by `path`; each object is exactly `{ "path": <fragment relative path>, "sha256": <sha256 hex of that fragment file> }`. `actions_fingerprint` is the SHA-256 digest of a canonical JSON object exactly `{ "path": <absolute action overlay path>, "sha256": <sha256 hex of the action overlay file> }`. The canonical JSON for fingerprints uses sorted object keys recursively, no pretty printing, and one trailing newline before hashing. `config_fingerprint` is the SHA-256 digest of the exact config file bytes plus the requested profile string separated by one NUL byte. `ledger_digest` is the SHA-256 digest of the exact `kev-ledger.json` bytes. `generation_max` is the maximum integer `generation` across the fragment entries in the index, or `0` when the fragment list is empty.

## Resume, rebuild, and failure behavior

When `--resume-from` is supplied, it must point to a JSON state file inside `/app`. The current config fingerprint, input fingerprint, and actions fingerprint must match the resume state before any success artifacts are written. A mismatch is a run-level failure with reason `resume_fingerprint_mismatch`. A valid resume still rebuilds all success artifacts from current inputs into the requested output directory and must be byte-stable with a normal run. The resumed run must also refresh both state locations: `state/kev-ledger.state.json` under the output directory and `--state-dir/kev-ledger.state.json` when the separate state directory is used.

On any run-level failure, validate paths before creating output directories or state directories. If path validation fails, the only permitted filesystem change is replacing a safe pre-existing output-directory `error-report.json` leaf symlink with the local regular error report. After validation, remove stale success artifacts from the output directory and write only `error-report.json`. The error report is canonical JSON with exactly `schema_version: "kev.error.v1"`, `profile`, `reason`, and `details`. Path-related errors use `details: {"path": "<reported path>"}`. Unknown signer errors use `details: {"signer": "<reported signer>"}`. Other run-level errors use an empty details object unless a row above specifies otherwise. Row-level catalog and action validation problems are not run-level failures; they appear in successful `kev-ledger.json` under `invalid_rows` and `invalid_actions` unless the input/index/config/action file itself is unreadable or unsafe.
